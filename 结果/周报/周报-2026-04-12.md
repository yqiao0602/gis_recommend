## 二、文献 1：MiniGeoSolver

 MiniGeoSolver 方法概要

  核心思想：渐进式两阶段微调（Progressive Strategy）

  把「NL → GIS 工具调用序列」这个复杂任务拆成两步，各训练一个 LoRA 适配器。

  阶段 1 — MiniGeo-Explore（工具选择 + 骨架规划）

  - 训练数据: TrainData1 — 400 条（GPT-4 生成）
  - 输入: 自然语言任务描述 + 完整 32 个工具列表
  - 输出格式:
    Framework: I can solve this task, and I will first use Get POI By Keywords
    for obtaining parks data, and then I will use Aspect for determining slope
    direction, finally I can obtain the results.
  - 学什么: 从 32 个工具中选出需要哪些工具、以什么顺序调用（宏观规划）
  - 产出: LoRA-Step1 适配器

  阶段 2 — MiniGeo-Workflow（详细工作流生成）

  - 训练数据: TrainData2 — 400 条
  - 输入: 自然语言任务 + 已选定的工具列表 + 阶段 1 输出的 Framework
  - 输出格式:
    Workflow: [Slope, (./elevation.tif), (./slope_output.tif)];
            [Kriging, (./plants.shp, 'count'), (./predicted_distribution.tif)];
  - 学什么: 给定工具集合后，生成带具体参数（输入路径、输出路径）的执行序列
  - 产出: LoRA-Step2 适配器

  推理流程

  NL 任务
     ↓
  [Gemma-2-2b + LoRA-Step1]  →  Framework（选哪些工具、什么顺序）
     ↓
  [Gemma-2-2b + LoRA-Step2]  →  Workflow（每个工具的具体参数和数据流）

  模型 & 训练细节

  ┌─────────────┬─────────────────────────────────────────────────────────┐
  │    项目     │                           值                            │
  ├─────────────┼─────────────────────────────────────────────────────────┤
  │ 基座模型    │ Gemma-2-2b (2B 参数)                                    │
  ├─────────────┼─────────────────────────────────────────────────────────┤
  │ 微调方式    │ LoRA (rank=8, alpha=32, dropout=0.05)                   │
  ├─────────────┼─────────────────────────────────────────────────────────┤
  │ LoRA 目标层 │ q/k/v/o_proj + gate/up/down_proj (全部 attention + MLP) │
  ├─────────────┼─────────────────────────────────────────────────────────┤
  │ 学习率      │ 1e-4, cosine, warmup 0.03                               │
  ├─────────────┼─────────────────────────────────────────────────────────┤
  │ 训练轮次    │ 1 epoch                                                 │
  ├─────────────┼─────────────────────────────────────────────────────────┤
  │ 序列长度    │ 4096                                                    │
  ├─────────────┼─────────────────────────────────────────────────────────┤
  │ 量化        │ 8-bit                                                   │
  ├─────────────┼─────────────────────────────────────────────────────────┤
  │ 训练框架    │ DeepSpeed ZeRO-2, 2x GPU                                │
  └─────────────┴─────────────────────────────────────────────────────────┘

  工具集

  - 27 个基础 GIS 工具: Buffer, Union, Intersect, Clip, Erase, Select, Near, Frequency, Get POI, Kriging, Kernel Density, Slope, Aspect, Visualization 等
  - 5 个扩展工具: raster2vector, Resample, NDVI, Summary Statistics, Mosaic
  - 每个工具定义了 Function / Input / Output / Demo

  评估

  - 500 条测试样本（同时测 Framework 和 Workflow）
  - 还做了数据量消融实验（100%/75%/50%/20% 训练数据）

  对照来看：

  MiniGeoSolver 的 Tool 和 QGIS 算子 基本是一一对应的，只是他们用了更抽象的自然语言名称：

  - Buffer → 对应 QGIS 的 native:buffer
  - Union → 对应 qgis:union
  - Intersect → 对应 qgis:intersection
  - Clip → 对应 qgis:clip
  - Erase → 对应 qgis:difference（QGIS 里叫 Difference）
  - Select → 对应 qgis:selectbyexpression
  - Near → 对应 ArcGIS 的 Near / QGIS 的 qgis:distancetonearesthubpoints
  - Slope → 对应 gdal:slope
  - Aspect → 对应 gdal:aspect
  - Kernel Density → 对应 qgis:heatmapkerneldensityestimation
  - Kriging → 对应 QGIS 的插值工具
  - Create Thiessen polygons → 对应 qgis:voronoipolygons

  但有几点关键区别：

  1. 粒度不同。他们只有 32 个工具，每个工具的输入输出定义得很清晰（一句话描述 Function、明确的 Input/Output 格式）。我们的算子集更大，而且有 L1/L2/L3 的层级结构。
  2. 没有用 QGIS 的原生标识符。他们定义的是逻辑层面的"工具"——"Buffer 就是做缓冲区"，不关心底层是 QGIS 还是 ArcGIS 实现。实际上他们代码里也有一些明显来自 ArcGIS 概念的工具

  3. 参数简化。QGIS 的 native:buffer 有很多参数（距离、段数、端点样式、溶解等），他们简化成只有"shapefile path + buffer radius"。Workflow 里生成的也只是路径级参数，不涉及算法内部的详细配置。

  所以本质上，MiniGeoSolver 的 Tool 就是我们说的算子，只不过他们工作在一个更抽象、更小的算子空间上，而且每个算子的参数接口被大幅简化了。

  他们的每个 Tool 都是一个具体可执行的算法操作（Buffer、Clip、Slope、Kriging...），不是分类也不是类别，直接对应到一次具体的 GIS 处理动作。这和你们 L3 的定位一致——L3 就是最终要调用的那个具体算法。

  区别只是：
  - 你们的 L3 数量更多，而且上面还有 L1/L2 的层级分类结构
  - 他们只有扁平的 32 个，没有层级，直接全部列在 prompt 里让模型从中选

  换句话说，MiniGeoSolver 做的事情等价于：给定自然语言，从 32 个 L3 算法中选出若干个并排好序，再给每个填上参数。只不过他们的 L3 空间比你们小得多，所以能把全部 32 个工具描述塞进一个 prompt 里让 LLM 直接看着选。

### 2.1 基本信息

- 题目：`MiniGeoSolver: Enhancing small language models for autonomous geospatial tool sequences generation through progressive strategy`
- 来源：`Environmental Modelling and Software`
- 关键词：`Small language model`、`Tool sequences`、`Progressive strategy`、`GeoAI`

### 2.2 研究背景与问题

论文关注的核心问题是：如何让小语言模型自动生成解决地理空间任务所需的工具序列。

作者认为，虽然大语言模型在多步工具调用上能力较强，但其部署成本高、推理代价大，不利于大规模落地。而小语言模型虽然轻量、易部署，但如果直接让其一步生成完整的工具序列，往往会因为推理链路过长、规划与执行耦合过深而失败。

因此，这篇论文要解决的并不是“模型能不能生成一句答案”，而是“模型能不能稳定地规划并输出一条可执行的地理工具工作流”。

### 2.3 核心思想

这篇论文最核心的思想是 `progressive strategy`，即渐进式两阶段生成。

作者认为，复杂地理任务的求解过程不应一次性直接输出完整 workflow，而应拆成两个连续阶段：

- 第一阶段先生成一个较抽象的 `Framework`
- 第二阶段再根据这个 `Framework` 生成更细化、更可执行的 `Workflow`

这种设计的本质是先做粗粒度规划，再做细粒度执行，从而降低模型一次性完成复杂推理的负担。

### 2.4 整体路线

从论文摘要、复现代码和数据组织来看，MiniGeoSolver 的整体路线可以概括为：

`自然语言任务 -> 生成求解框架 Framework -> 根据 Framework 生成工具工作流 Workflow -> 输出最终工具序列`

其中：

- `Framework` 负责回答“这类任务大致要用哪些工具、按什么大致顺序解决”
- `Workflow` 负责回答“每一步具体调用什么工具、输入输出如何衔接、最终形成怎样的处理链”

这种设计相当于把原本“从任务到完整工具链”的一步映射，拆成了两个难度更低的子问题。

## 三、文献 2：Geo-CLASS

### 3.1 基本信息

- 题目：`Extraction of geoprocessing modeling knowledge from crowdsourced Google Earth Engine scripts by coordinating large and small language models`
- 来源：`International Journal of Geographical Information Science`
- 关键词：`Geoprocessing`、`Large language model`、`Prompt engineering`、`Chain of thought`、`Ontology mapping`

### 3.2 研究背景与问题

这篇文献关注的不是“根据自然语言生成工作流”，而是“如何从已有的大量 GEE 脚本中抽取地理处理知识”。

作者的出发点是：

- GEE 上已经积累了大量众包脚本
- 这些脚本本身就是实际地理处理流程的知识载体
- 如果能从这些脚本中自动抽取主题、功能、数据源及其关系，就可以进一步支持知识图谱构建、领域推理和后续的脚本生成

因此，Geo-CLASS 的研究对象是“已有脚本”，目标是“知识抽取与知识组织”。

### 3.3 核心思想

这篇文献的核心思想是：`LLM 负责抽取，SLM 负责标准化`。

作者认为：

- 小模型适合做语义嵌入和相似度匹配，但不擅长处理复杂代码
- 大模型擅长理解和总结脚本，但其输出往往缺乏统一、稳定的地学术语体系

因此，论文提出了一种协同框架：

- 先由大模型基于领域 schema 和 prompt，从脚本中抽取知识描述
- 再由小模型将这些自然语言描述映射到已有领域知识库中的标准概念

这一思路的关键不是让模型直接产出“最终知识图谱”，而是通过“先抽取、后标准化”的两段式流程提高一致性和可用性。

### 3.4 论文中的知识对象

从论文摘要、正文首页和代码仓库可以看出，Geo-CLASS 关注的知识对象主要包括：

- `Theme`
- `Function`
- `DataSource`
- `Relation`

论文正文还提到脚本中包含：

- `Time scope`
- `Spatial scope`

以及这些要素之间的关系。

因此，Geo-CLASS 更像是在构建一套“地理处理知识的语义表示框架”，而不是直接生成具体平台上的算子链。

### 3.5 整体路线

Geo-CLASS 的整体路线可以概括为：

`GEE 脚本 -> 预处理 -> LLM 抽取实体与关系 -> 结果结构化 -> SLM 标准化映射 -> 评估`

如果按仓库结构拆开，可以进一步写成：

1. 脚本预处理
2. 基于 schema-aware prompt 的知识抽取
3. 将抽取结果从 JSON 整理成 CSV
4. 用小模型向量化并映射到统一概念库
5. 对实体和关系抽取结果进行评估

### 3.7 文中方法流程

结合论文摘要和代码实现，这篇文献的方法大致可以概括为以下流程：

1. 从大量 GEE 众包脚本中选取样本。
2. 对脚本文本进行预处理，尽量减少噪声和无关注释干扰。
3. 设计面向地理处理任务的 schema-aware prompt。
4. 使用大模型抽取主题、功能、数据源以及它们之间的关系。
5. 将抽到的自然语言描述映射到知识库中的标准概念。
6. 计算实体识别和关系识别的精度、召回率、F1 等指标。

这一路线体现出一个很明显的设计哲学：

- 复杂脚本理解交给大模型
- 术语统一与概念归一交给小模型和知识库

### 3.8 数据与实验

根据论文摘要：

- 研究从 `295,943` 个脚本中选取样本
- 最终实验基于 `237` 个 GEE 脚本展开
- 与 `Llama-3`、`GPT-3.5`、`GPT-4o` 等基线进行了比较

论文摘要中还给出结果：

- 实体识别准确性最高提升 `31.9%`
- 关系识别准确性最高提升 `12.0%`

这说明该方法在“把脚本中的自由表达知识映射成较规范的领域知识”这件事上取得了明显增益。

### 3.9 文献特点总结

这篇文献的主要特点可以概括为：

- 关注对象是 `已有地理处理脚本`，而不是自然语言任务描述
- 研究目标是 `知识抽取与标准化`，而不是直接生成工作流
- 强调 `schema-aware prompt + ontology mapping`
- 强调 `大模型抽取 + 小模型标准化` 的协同方式
- 最终服务于知识图谱、领域推理和 RAG 等更上层的应用

如果只从文献本身来看，Geo-CLASS 提供的是一条比较典型的“从脚本到知识”的路线：先理解脚本，再抽概念，再统一术语，再做结构化组织。

## 四、两篇文献的汇总认识

从本周阅读来看，这两篇文献分别代表了地理空间智能中的两个不同方向。

### 4.1 MiniGeoSolver 的代表性

MiniGeoSolver 代表的是：

- 面向任务求解
- 面向工作流生成
- 面向多步工具调用
- 通过渐进式训练降低生成难度

它关注的是“如何把任务拆开，并让模型一步一步生成可执行流程”。

### 4.2 Geo-CLASS 的代表性

Geo-CLASS 代表的是：

- 面向脚本知识挖掘
- 面向术语标准化
- 面向知识图谱与知识底座建设
- 通过大模型与小模型协同提高知识抽取质量

它关注的是“如何把已有脚本沉淀成结构化领域知识”。

### 4.3 总体印象

两篇文献虽然切入点不同，但都体现出一个共同趋势：

- 复杂地理空间问题不再适合简单地交给单一模型端到端完成
- 更有效的方式往往是将流程拆解为多个阶段
