- 当前怎么提精度
  - 系统最终要长成什么样
  - 最后论文/报告怎么做横向对比

  这三件事不能同时推进。否则每一步都在变，最后你根本不知道精度到底是哪个改动带来的。

  我建议你先强行拆开。

  先定主任务
  现在最重要的事只有一件：

  先提升当前系统精度，并且把提升来源说清楚

  所以短期内不要同时上两个大模块。
  我的建议是：

  - 先做 reranker / verifier
  - 暂缓骨架规划模块

  原因很简单：

  - reranker / verifier 离你们当前代码最近，仓库里已经有现成积木
  - 它改动小，见效最快
  - 它能先回答一个关键问题：
    当前模型生成的 top-N 候选里，到底有没有正确答案？

  这个问题非常关键。

  如果 top-N 里经常已经有较好的候选，只是 top-1 选错了，那你现在该做的是 reranker / verifier。
  如果 top-N 里本来就很少有对的候选，那才说明你需要更前置的 骨架规划模块。

  所以这两个模块不是并列马上做，而是有先后关系。

  我建议的顺序
  按你们当前状态，最稳的是这条线：

  1. 跑完当前补充实验，锁定一个稳定 baseline
     也就是从 off / soft / hard + threshold 里确定当前最优设置。
  2. 在这个 baseline 上先接 reranker / verifier
  3. 做一次 top-N oracle analysis
     看 top-3 / top-5 / top-10 里是否明显有更好候选
  4. 如果 oracle gap 很大，再上 骨架规划模块
  5. 等主线稳定后，再做 LLM / MiniGeoSolver 风格 横向对比

  这条顺序最重要。

  你现在不要同时做两件事
  所以我给你一个非常明确的建议：

  - 后续计划.md 里提到的两个模块，不要现在一起开工
  - 先只把 reranker / verifier 作为 P1
  - 骨架规划模块 作为 P2，但前提是先看 oracle 分析结果

  这能把你的混乱感降很多。

  为什么 MiniGeoSolver 有参考价值，但不是现在立刻照搬
  你现在觉得 MiniGeoSolver 很有参考价值，这个判断是对的。
  但它最值得借的是：

  - 两阶段思想
  - 显式中间表示
  - 先 framework / skeleton，再 workflow

  它不是说你现在立刻要把整套系统全部改成 SFT 小模型方案。
  对你们当前项目来说，更合理的吸收方式是：

  - 现在先保留 V4.6 + set predictor
  - 先补 reranker / verifier
  - 等确认 top-N 里确实“有好候选但排序不对”之后
  - 再把 MiniGeoSolver 的思想落成你们自己的 骨架规划模块

  也就是说：

  - MiniGeoSolver 更像 P2 的参考
  - reranker / verifier 才是 P1 的直接落地项

  横向评估怎么放
  横向评估现在先不要急着做。
  现在做会有一个问题：你自己的系统还没定型，拿什么去比？

  我建议把横向评估放到后面，分两类：

  1. 当前主线内部消融

  - V4.6
  - V4.6 + set predictor
  - V4.6 + set predictor + reranker/verifier
  - V4.6 + set predictor + reranker/verifier + planner

  2. 外部方法横向对比

  - LLM direct generation
  - LLM progressive generation
    也就是 MiniGeoSolver 风格：先 framework，再 workflow
  - 如果条件允许，再加一个简单 retrieval baseline

  这样论文结构也会清晰很多。

  你现在最该做的事
  如果只保留一个最小行动清单，就是这个：

  - 跑完当前 4 组补充实验
  - 锁定当前 baseline
  - 不再继续扫 threshold
  - 下一步只做 reranker / verifier
  - 做 top-N oracle analysis
  - 再决定要不要上 骨架规划模块

  所以你现在不用想太散。
  当前阶段其实只需要回答两个问题：

  - 当前最佳 baseline 是谁？
  - 当前问题是出在“生成不到”，还是“选不好”？

  把这两个问题答清楚，后面的路就会顺很多。
