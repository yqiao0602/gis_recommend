你现在遇到的，其实已经不是“普通序列生成”问题了，而是一个非常典型的：

> **Workflow Planning / Program Synthesis / 多路径推理问题**

这类问题里，“一个目标存在多个等价执行路径”是核心特征，而不是异常情况。

你现在已经非常准确地把问题拆成了三个层面：

- 训练目标单解化（CE + Teacher Forcing）
- 推理图约束过硬（transition matrix）
- 评估指标只认 canonical path

这个分析方向是对的，而且实际上已经接近很多 workflow/planner 类论文真正关注的问题了。

------

# 一、为什么 GPT / Claude “天然支持多解”

你这里有个非常关键的问题：

> 为什么 GPT 类模型能理解多解，而我的模型不行？

核心原因不是“聪明”两个字，而是：

------

## 1. GPT 学的是“分布”，不是“唯一答案”

你现在的训练方式本质是：

```text
输入 -> 唯一标准序列
```

CE loss 强制：

```text
P(正确token)=1
P(其它token)=0
```

这会导致：

```text
NDVI -> 裁剪   （被强化）
裁剪 -> NDVI   （被压制）
```

模型学到的是：

> “只有这一条路径是正确的”

而 GPT 的训练数据里：

```text
同一个任务
可能出现几十种表达
几十种步骤顺序
```

所以它学到的是：

```text
多个 token 都可能合理
```

即：

```text
P(A)=0.55
P(B)=0.35
P(C)=0.1
```

而不是 one-hot。

这本质上是：

# 你的模型在学“标准答案”

# GPT 在学“条件概率分布”

------

# 二、你现在的问题本质：Workflow 存在偏序（Partial Order）

你这个 NDVI 例子，本质是：

```text
裁剪 与 NDVI
不存在严格依赖顺序
```

即：

```text
Crop -> NDVI
NDVI -> Crop
```

都满足 DAG 约束。

这属于：

# 偏序规划（Partial-order Planning）

而你当前模型做的是：

# 全序列建模（Total-order Sequence Modeling）

这是根本矛盾。

因为 Transformer Decoder 默认假设：

```text
token_1
必须先于
token_2
```

但很多 GIS workflow 根本不是全序。

------

# 三、你当前系统最危险的问题

其实不是 loss。

而是：

# allowed_next transition matrix

这是目前最容易把模型“训死”的地方。

因为它实际上在做：

```python
硬规则剪枝
```

类似：

```python
if next_token not in allowed_next[cur]:
    prob = -inf
```

这会导致：

- 模型即使认为方案 B 正确
- beam search 也永远走不到

即：

# 推理阶段比训练阶段还保守

这是很多 constrained decoding 最大的问题。

------

# 四、真正可行的解决方向（重点）

你这个问题，其实有几个层级的解决方案。

------

# 方案一（最重要）：从“单参考”变成“多参考训练”

这是第一优先级。

------

## 你现在：

```text
Input:
计算NDVI

Target:
[NDVI, Crop]
```

应该变成：

```text
Targets:
1. [NDVI, Crop]
2. [Crop, NDVI]
```

训练时：

```python
loss = min(
    CE(pred, target_A),
    CE(pred, target_B)
)
```

或者：

```python
loss = average(...)
```

这叫：

# Multi-reference Training

在：

- machine translation
- code generation
- planning
- dialogue

里非常常见。

------

## 更进一步：动态等价路径生成

你甚至可以：

基于 workflow DAG 自动生成：

```text
所有合法 topological ordering
```

例如：

```text
A -> C
B -> C
```

可以生成：

```text
A,B,C
B,A,C
```

然后全部作为训练样本。

这一步非常关键。

因为：

# 你不是在扩数据

# 你是在显式告诉模型：

# “这些路径等价”

这是认知层面的改变。

------

# 方案二：不要用硬 transition matrix

你现在大概率是：

```python
mask illegal token
```

建议改成：

# soft constraint

例如：

```python
score = model_score + λ * graph_score
```

而不是：

```python
illegal -> -inf
```

即：

------

## 从：

```text
不允许
```

改成：

```text
不推荐
```

------

比如：

```python
final_score =
    lm_score
    + 0.3 * graph_transition_score
```

而不是：

```python
if illegal:
    ban
```

因为训练数据不完整。

你的 transition matrix 其实只是：

# “历史统计”

而不是：

# “真理”

这是巨大区别。

------

# 方案三：从 Sequence 转向 DAG / Set / Plan 建模（这是长期方向）

这是更高级但也更正确的方向。

因为 GIS workflow 本质上是：

```text
操作图
```

不是：

```text
自然语言句子
```

所以未来更合理的是：

------

## 1. 预测操作集合（Set Prediction）

先预测：

```text
需要哪些算子
```

而不是顺序。

你之前其实已经开始做了。

这是对的。

------

## 2. 再做依赖排序

例如：

```text
Step1:
预测集合
{Crop, NDVI, RasterCalc}

Step2:
预测依赖边
Crop -> NDVI ?
NDVI -> Crop ?
```

最后：

```text
拓扑排序
```

生成 workflow。

------

这其实已经接近：

# program synthesis

# task planning

# graph generation

方向了。

很多论文已经不做纯 AR decoder 了。

因为：

# Workflow 天然不是语言

------

# 五、评估指标必须换

这是你现在最被低估的问题。

------

## token_accuracy 完全不适合你

因为：

```text
[Crop, NDVI]
```

和：

```text
[NDVI, Crop]
```

语义等价。

但：

```text
exact_match = 0
```

这是错误评估。

------

# 你应该增加：

------

## 1. Set-level F1

只看：

```text
用了哪些算子
```

不看顺序。

------

## 2. DAG equivalence

判断：

```text
是否满足依赖约束
```

而不是：

```text
token 是否逐位置一致
```

------

## 3. Executability

最重要。

直接：

```text
能不能运行
```

这个比 token accuracy 更重要。

很多 program synthesis 论文已经：

# execution accuracy > exact match

因为：

```python
a+b
b+a
```

完全等价。

------

# 六、你现在最适合的路线（结合你当前系统）

我其实很建议你：

------

# 短期（最现实）

## 1. Multi-reference augmentation

自动生成合法 reorder。

------

## 2. transition matrix 改 soft constraint

不要 hard mask。

------

## 3. beam search 保留多样性

加入：

- diverse beam search
- stochastic beam
- top-p decoding

别只保留最优路径。

------

## 4. evaluation 改 execution-based

这是论文创新点。

------

# 中期（最重要）

从：

```text
AR token generation
```

逐渐转：

```text
Set + Dependency Prediction
```

你之前做 set predictor 其实已经踩对方向了。

------

# 七、你现在其实已经接近“研究问题”了

你这个问题已经不是：

```text
怎么调参
```

而是：

# “如何建模 GIS workflow 的多解规划性”

这其实是很好的论文点。

因为你现在已经发现：

> “GIS workflow 并非唯一序列，而是约束下的等价执行空间”

这个表述其实已经有研究味道了。

------

# 八、最后回答你最核心的问题

> 是因为我的模型参数量太小吗？

有影响。

但不是根因。

真正根因是：

------

## GPT 学的是：

```text
开放世界概率分布
```

而你现在训练的是：

```text
单路径监督分类器
```

------

即使你把模型放大：

```text
7B
13B
```

如果：

- loss 不变
- 数据不变
- transition hard mask 不变
- exact match 不变

它依然会：

# “认为只有一个正确答案”

所以问题本质是：

# 建模范式问题

而不是单纯参数量问题。
