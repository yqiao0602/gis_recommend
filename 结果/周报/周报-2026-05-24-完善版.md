# 乔雲周报20260524

## 一、目前进展

本周继续围绕“自然语言到 GIS 工作流推荐”系统开展实验、代码修复和训练前准备。相比上周，本周工作的重点发生了明显变化：不再继续停留在报告层面的观察和审计，而是开始围绕已经识别出的六个核心问题进行实质修复，包括多解问题、工作流复杂度问题、纯生成不稳定问题、评价体系错位问题、候选排序问题和语义约束问题。

目前可以比较明确地判断，当前系统不能再被简单理解为“输入任务文本，然后由 Transformer 一次性生成唯一正确工作流”。GIS 工作流本身存在多解性，同一任务可能有多条合理的算子链；同时，很多任务的可用性并不取决于是否逐 token 复现某一个参考答案，而取决于算子集合是否合理、流程逻辑是否成立、能否映射到 QGIS 算子以及最终链条是否具备可执行性。因此，本周进一步把系统定位从 sequence generation 调整为 workflow planning：系统应先构造候选工作流，再通过约束、可用性和证据进行选择。

围绕这一定位，本周主要形成了三条实质推进线。第一是评价体系校准，把原来更偏“像不像标准答案”的指标，改成更能反映系统是否真的好用的指标。第二是训练入口和训练数据修复，保证训练时不再把单一参考答案当成唯一正确答案。第三是多解训练数据扩充，从原来 42 条人工确认的等价变体，扩展到当前高置信的 1,841 条多解训练样本，为后续训练消融提供了更有影响力的数据基础。

## 二、本周主要工作

### 1. 明确评价体系从“像不像答案”转向“能不能使用”

本周首先重新确认了当前评测指标的问题。过去的指标更关注“生成结果和某一条参考答案有多像”，但 GIS 工作流不是单答案任务，同一个需求可能存在多条合理流程。如果仍然只按参考序列逐步比较，就会把一些可用流程误判为错误。

因此，本周将评估重点调整为：看关键算子是否覆盖、流程是否可用、能否执行、能否映射到 QGIS。原来的逐 token 准确率和完全匹配率仍然保留，但只用于分析模型行为，不再作为最终准确度结论。这个调整的意义在于，后续系统优化会直接面向“推荐出的算子链是否真的有用”，而不是追求复现某一条唯一参考流程。

同时，本周修复并完善了 evidence-aware ranking 的离线校准脚本。该脚本只读取已有 planner 或 evaluation report，不修改主链路输出，用于比较 legacy selection、evidence-aware selection 和候选池上限之间的差异。它的判定逻辑也已经改为基于主指标，而不是简单看 evidence-aware 是否和 legacy 选择不同。

### 2. 完成模型训练链路准备

本周把 Transformer 和 Set Predictor 两条训练入口都做了整理，使它们能够明确使用多解训练数据，并且在训练前输出当前数据、指标和 checkpoint 规则，避免后续训练时用错数据版本或误解训练结果。

真正重要的是训练目标的变化：后续 Transformer 不再只是学习复现某一条固定参考 workflow，而是通过多解样本看到“同一个任务可以有不同合理实现”。预期收益是减少模型对唯一答案的过拟合，让生成候选更容易覆盖合理算子集合，并降低因为局部顺序不同导致的误判。

Set Predictor 也同步接入多解参考。它的作用是预测一个任务可能需要哪些算子，过去只看单一参考答案时，某些合法替代算子会被当成“不该出现”。现在使用多解参考后，训练目标会更接近“覆盖合理算子集合”，有利于提高候选池覆盖度。它本身仍然不是排序器或语义验证器，最终效果还需要在 Planner 层面看可用率和 QGIS 落地情况。

### 3. 扩充多解训练数据并设计消融实验

本周围绕多解训练数据做了较大推进。原来的人工等价样本数量很少，只能说明“多解现象存在”，但很难真正影响模型训练。因此，本周从质量门禁训练集中自动挖掘潜在多解样本，再通过审查、过滤和分层合并，形成了一版更适合训练的多解数据集。

这批数据主要包括两类：一类是同一任务下的不同实现方式，用来教模型理解“同一个 GIS 任务可以有多种合理流程”；另一类是低风险的局部步骤交换，用来补充工作流顺序变化的训练样本。对于风险更高、还需要进一步确认的候选，本周没有直接放入训练集，而是先保留为待审样本。

最终，多解训练样本从原来的几十条扩展到约一千八百条，并生成了隔离的训练数据版本。这个数据集只修改训练集，不改变验证集和测试集，因此后续可以比较公平地观察多解训练是否真正提升模型效果。

本周还梳理了后续训练实验的对比关系。当前不应该只训练一个版本，而应该保留多组 ablation：baseline、`mr_all_42`、`mr_all_220`、`mr_all_1257` 和 `mr_all_1841`。这样可以判断多解样本规模扩大后，系统是否真的更容易给出可用工作流，而不是只在字面上更接近参考答案。

其中 `mr_all_1841` 是目前最高置信的大规模版本，但它不应该直接替代所有较小实验。更合理的做法是先看较小数据版本是否有正向趋势，再使用 `mr_all_1841` 做下一轮规模验证。这样可以避免把不同来源的数据效果混在一起解释。

这组实验如果有效，预期收益主要体现在三个方面：一是推荐出的算子集合更完整，关键步骤缺失会减少；二是候选 workflow 的可用率提高，系统更容易从候选池中选到能用的链；三是最终 QGIS 落地率提高，也就是推荐结果更接近真正可运行的 QGIS 算子链。

## 三、当前结果分析

第一，系统的核心问题已经从“模型是否能逐 token 复现参考答案”转为“系统是否能规划出可用工作流”。这是本周最重要的认识变化。后续不能再只围绕 TokenAcc 或 Sequence EM 优化，否则会继续和 GIS 多解任务的真实目标错位。

第二，多解训练数据已经从概念验证进入可训练规模。原来的 42 条 MRV 样本只能说明多解现象存在，但很难影响模型；当前 1,841 条高置信样本已经达到约 3% 的训练注入率，虽然仍不是很大，但足以支撑严肃的训练消融实验。

第三，多解数据质量目前是分层可控的。MRV v2 的 42 条最可靠；结构等价的 584 条信息量最高，但内部存在强弱差异；filter/filter 交换的 1,215 条较稳定，但主要教模型局部顺序不敏感。风险较高的 select/filter 和 select/clip 候选没有进入训练集，这一点保证了当前 `mr_all_1841` 的高置信边界。

第四，训练脚本已经具备重新启动训练的基本条件。Transformer 和 Set Predictor 都已经支持多解训练数据路径，并且训练前会明确输出数据、指标和 checkpoint 契约。相比之前，这降低了误用旧路径、误看指标或训练错数据版本的风险。

第五，排序和语义约束仍然不是训练脚本本身能完全解决的问题。多解训练可以缓解模型对唯一参考答案的过拟合，长度统计可以缓解部分复杂度问题，但候选排序、语义兼容性和 QGIS 落地仍然需要 Planner、reranker 和 constraint 层继续优化。训练是当前重要一步，但不是全部系统问题的终点。

## 四、后续计划

1. 在服务器上启动分组训练实验。先比较原始数据版本和多解数据版本，观察多解训练是否能提升推荐结果的可用性。

2. 训练后使用新的评价体系进行统一评估。重点不再看是否完全复现参考答案，而是看关键算子是否覆盖、流程是否可用、能否执行、能否落到 QGIS。

3. 继续完善候选式 workflow planning。训练完成后，把新模型输出接入候选池，与历史检索候选、可用性规则和 QGIS 映射一起比较，判断最终选择是否更稳定。

4. 继续治理多解样本。对目前暂未纳入训练的高风险候选继续抽检，确认安全后再考虑扩充；不稳定的样本保留为边界案例，不直接进入训练。

## 五、本周小结

本周的主要进展不是单个模型指标提升，而是把系统从“继续分析问题”推进到“训练前可执行修复”。评价体系已经纠偏，训练入口已经加固，多解训练数据已经扩展到可训练规模，并且高风险候选被隔离。下一阶段的重点应转向服务器训练和同口径评估，用实际的“可用率、可执行率、QGIS 落地率”和关键算子命中情况，判断这些修复是否真正提升推荐出的算子链质量。
