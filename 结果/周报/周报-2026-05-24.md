## 一、评价体系重构：从 Sequence Generation 到 Workflow Planning

### 1.1 问题诊断

当前系统的评估指标存在"世界观分裂"：

- **Tier 1（旧世界观）**: `sequence_em`, `token_accuracy`, `lcs_ratio` — 衡量"生成结果像不像参考答案"
- **Tier 2/3（新世界观）**: `usable`, `qgis_mapping_rate`, `logic_consistency` — 衡量"workflow 能不能在 QGIS 里跑通"

这两个目标函数已经不一致。实测中常见 `sequence_em` 很低但 `usable=True` 的情况——说明参考答案不是唯一正确 workflow（多解性问题的直接证据）。

### 1.2 新评价体系（五层架构）

| 层级 | 定位 | 核心指标 | 用途 |
|------|------|----------|------|
| **Tier 1** | 诊断层（降级） | `token_accuracy`, `sequence_em`, `set_f1`, `lcs_ratio`, `length_ratio` | 诊断模型行为，不再是主 KPI |
| **Tier 2** | 核心层（升级为主 KPI） | `usable`, `usability_score`, `qgis_mapping_rate`, `workflow_logic_consistency`, `harmful_step_rate`, `required_step_coverage` | 衡量 workflow 实际可用性 |
| **Tier 3** | 系统层（升级） | `selected_top1_usable_rate`, `pool_top3/5_any_usable_rate`, `top1_usable_delta_vs_retrieval`, `set_coverage_score` | 衡量 Candidate Pool + Rerank 系统能力 |
| **Tier 4** | 复杂度层（新增） | `early_eos_rate`, `mean_length_ratio`, `mean_selected_length vs mean_reference_length` | 检测生成长度偏差（当前核心问题之一） |
| **Tier 5** | 研究层 | canonicalized metrics, equivalence coverage, MR hit rate | 多解性研究验证 |

### 1.3 关键改动

1. **`sequence_em` 重新定义为"历史 workflow 重现率"**，而非"正确率"
2. **`TopK any usable` 成为多解性友好指标**：Top5 里有一个可用就说明系统覆盖到了某种正确方案
3. **新增 `early_eos_rate`**：长任务被过早截断的比例（`selected_length < expected_length * 0.6`）
4. **Planner 报告重组**：主 KPI (Tier 2/3) 前置，复杂度诊断 (Tier 4) 紧随，序列相似度 (Tier 1) 降级为诊断附录
5. **Per-task CSV 增加复杂度列**：`mean_selected_length`, `mean_reference_length`, `early_eos_rate`

### 1.4 代码改动清单

| # | 文件 | 改动 |
|---|------|------|
| 1.4.1 | `scripts/run_v4_qg_planner.py` | per_sample 新增 `complexity` 字段（`expected_length`, `selected_length`, `is_early_eos`） |

## 二、三主线并行推进

### 2.1 系统定位变化

系统已从"训练一个 Transformer 输出 workflow"演进为 **GIS Workflow Planning System**：

```
以前: Task → Transformer → Workflow
现在: Task → Retrieve + Generate Candidates → Constraint-aware Planning → Best Workflow
```

Transformer 只是 candidate proposer 之一，不再是唯一生成器。

### 2.2 三条主线的本质

| 主线 | 本质 | 解决什么问题 |
|------|------|-------------|
| **Candidate Pool + Rerank** | historical prior | "从哪里开始" — 提升 usable rate |
| **Length / Complexity Modeling** | planning depth | "需要规划多深" — 消除生成长度偏差 |
| **MR / Workflow Equivalence** | semantic ambiguity | "哪些路径也算对" — 研究创新 + 长期正确性 |

### 2.3 Track 1: Candidate Pool Planner 正式成型 (Priority 1)

#### 目标
不再完全依赖模型"从 0 生成"，而是检索 + 生成候选池 → 约束感知重排序 → 选最优。

#### 已完成的改动

| # | 改动 | 文件 | 说明 |
|---|------|------|------|
| 2.3.1 | Score contamination 修复 | `run_v4_qg_planner.py:202-203` | `merge_candidate_pool` 不再用 `candidate.get("score")` 跨源回填 `retrieval_score` / `model_score` |
| 2.3.2 | Task-conditioned length score | `run_v4_qg_planner.py` | 新增 `_load_length_stats()`, `_task_expected_length()`；reranker 的 `length_score` 从硬编码 `expected_length=8` 改为查 `task_type_length_stats.json` 的 per-type median |
| 2.3.3 | Rerank 权重调整 | `PlannerWeights` | `length`: 0.02→0.08, `retrieval`: 0.07→0.04, `model`: 0.04→0.01 |
| 2.3.4 | Set Predictor preflight | `run_v4_qg_planner.py:578-581` | 当 Set Predictor 预测 < 2 tokens 时自动回退到频率统计 Set Prior |

#### 当前架构

```
Task
  ├─ LexicalRetrieval → retrieval TopK candidates
  ├─ V4 AR Beam Search → AR TopK candidates (optional, needs checkpoint)
  └─ Set Predictor / Fallback Frequency Prior → set coverage scoring
       ↓
  merge_candidate_pool (dedup by token tuple, source attribution)
       ↓
  rerank_candidates (11-feature weighted score)
       ↓
  Top1 / Top3 / Top5 workflows + usability evaluation
```

#### Rerank 特征权重（最终版）

| 特征 | 权重 | 类型 |
|------|------|------|
| `usability_score` | 0.35 | 规则可用性综合分 |
| `usable_bonus` | 0.35 | 可用性二值门槛奖励 |
| `set_coverage_score` | 0.18 | Set Predictor 覆盖度 |
| `qgis_mapping_rate` | 0.14 | QGIS 算子映射率 |
| `logic_consistency` | 0.12 | GIS 逻辑一致性 |
| `soft_transition_score` | 0.08 | 转移矩阵软评分 |
| `task_conditioned_length_score` | 0.08 | 任务条件化长度匹配（新增） |
| `retrieval_score` | 0.04 | TF-IDF/lexical 检索得分 |
| `model_score` | 0.01 | V4 AR 模型得分 |
| `critical_forbidden_penalty` | -0.35 | 严重违规惩罚 |
| `harmful_step_penalty` | -0.12 | 有害步骤惩罚 |
| `forbidden_penalty` | -0.04×N | 一般违规惩罚 |
| `redundancy_penalty` | -0.04 | 冗余惩罚 |

### 2.4 Track 2: Length / Complexity Modeling (Priority 2)

#### 问题根因

当前 AR Transformer 没有真正学会 `Task → Workflow Complexity → Workflow Length` 的映射。不同 GIS 任务天然需要不同复杂度：

| 任务类型 | 典型长度 | 问题 |
|----------|----------|------|
| NDVI | 短 (3-5) | 正常 |
| Flood Mapping | 中 (6-9) | 偶尔偏短 |
| SAR Rice Extraction | 长 (10-15) | 经常被过早 EOS |
| Multi-temporal Change Detection | 很长 (12-18) | 严重截断 |

根源：训练集中短 workflow 数量多 → EOS token 学得过强 → beam search 偏向短序列。

#### 已完成的改动

| # | 改动 | 文件 | 说明 |
|---|------|------|------|
| 2.4.1 | Length Bucket Predictor | **新文件** `src/gis_recommend/data/length_bucket_predictor.py` | 纯查表分类器，按 task type median 分 4 桶 |
| 2.4.2 | Task-adaptive EOS suppression | `infer_l3_candidates_v4.py` + `v4_qg.py` | 全局 `min_length` → bucket-adaptive `eos_suppress_until` |
| 2.4.3 | `set_complexity_profile()` | 同上 | 新增方法，调用 `LengthBucketPredictor` 设置 `eos_suppress_until` + `expected_length` |
| 2.4.4 | Bucket 分布分析脚本 | **新文件** `scripts/analyze_length_bucket_distribution.py` | 输出每个桶的 task type 分布、样本量、中位数 |

#### Length Bucket 定义

| Bucket | 长度范围 | median 条件 | min_length | EOS suppress until | 任务数 | 样本数 |
|--------|----------|-------------|------------|--------------------|--------|--------|
| `short` | 1-3 | ≤ 4 | 1 | 0 | 0 | 0 |
| `medium` | 4-6 | 5-7 | 3 | 2 | 7 | 549 |
| `long` | 7-10 | 8-12 | 5 | 4 | 33 | 33,932 |
| `very_long` | 10+ | ≥ 13 | 7 | 6 | 9 | 42,403 |
