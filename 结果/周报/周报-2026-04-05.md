# 周报：GIS 算子推荐系统优化（2026.03.31 - 2026.04.05）

## 一、本周工作概述

本周围绕“自然语言到工作流推荐”的核心链路，重点排查了当前推荐准确率偏低的原因。前期我们一直将问题更多归因于模型结构和参数设置，但本周通过训练迭代、代码复核和评估流程回查，基本确认：**当前准确率提升受限的主要原因，不是单纯的模型能力不足，而是训练与推理流程中存在结构性问题。**

本周的工作重点可以概括为两条线：

- 一条线是继续推进 Transformer 训练版本迭代，验证问题究竟出在模型本身，还是出在训练方式。
- 另一条线是对 Set Predictor 与 Transformer 的联合推理流程做系统复盘，判断第一阶段对第二阶段的影响是否被放大。

---

## 二、本周主要进展

### 1. 完成 Transformer 训练链路的系统排查

本周对 V4.2 至 V4.6 多个训练版本进行了连续复盘和对比，重点观察了 Teacher Forcing 指标、自回归生成指标以及模型保存逻辑。经过排查，已确认此前版本中存在若干影响训练效果的关键问题，包括：

- 自回归主损失没有真正回传到 BERT 编码层，导致文本理解部分没有从生成错误中充分学习。
- 长度损失、任务分类损失虽然被计入总损失，但实际没有发挥训练作用。
- 模型保存标准偏向 Teacher Forcing 指标，与最终真实推理目标存在偏差。
- 评估脚本没有严格复用训练时划分的测试集，历史评估结果存在偏乐观风险。

这些问题解释了为什么前几周虽然做了多轮版本优化，但效果始终不稳定、提升也不连续。

### 2. 推出并训练 V4.6 版本

针对上述问题，本周完成了 V4.6 版本的训练流程修正，主要包括：

- 打通自回归训练阶段的主梯度链路。
- 让辅助损失真正参与参数更新。
- 将 best model 的选择标准调整为更贴近真实生成效果的 AR 指标。
- 修复评估脚本，改为使用独立测试集。

从训练日志看，修复方向是成立的：

- BERT 梯度已恢复正常，不再是之前的“未生效”状态。
- AR-TokenAcc 达到目前版本中的相对较高水平。
- 训练与评估的口径比之前更一致，后续版本对比会更可信。

### 3. 明确了 Set Predictor 的核心问题不只是“预测不准”

本周同步审查了 Set Predictor 的训练与推理逻辑。结论是：**第一阶段的问题不仅是预测精度有限，更关键的是它对第二阶段的作用方式过于刚性。**

此前的联合推理中，Set Predictor 会以硬约束方式直接限制 Transformer 的可选输出。一旦第一阶段漏掉真实需要的 token，第二阶段即使本身有能力生成，也会被直接屏蔽。这种机制会显著放大第一阶段的误差。

基于这一判断，本周已将联合推理改造成三种可对比模式：

- `off`：不使用 Set Predictor
- `soft`：以软约束方式对高置信 token 做轻量引导
- `hard`：保留原有硬约束逻辑作为对照

这一步的意义在于，后续我们终于可以把“模型能力问题”和“联合策略问题”分开验证，而不是继续混在一起判断。

### 4. 完成 Set Predictor 重训与 `off / soft / hard` 三组对比评估

在完成训练脚本修复后，本周补充完成了 Set Predictor V3 的重新训练，并基于独立测试集完成了 `off / soft / hard` 三组联合评估。

评估结果表明，Set Predictor 本身已经能够稳定收敛，说明当前问题不再是“第一阶段训不起来”，而是“第一阶段的结果怎样参与第二阶段解码”。

从端到端表现看，联合链路已经真正生效，不再像此前那样三组结果完全一致。其中，`soft` 模式能够带来相对稳定且副作用较小的改善，是当前更合理的优化方向；`hard` 模式虽然在集合匹配层面更强，但会明显损伤长度和顺序相关表现，因此不适合作为默认方案。

这意味着，当前阶段更重要的工作已不是继续单独强化 Set Predictor，而是优化它与 Transformer 的协同方式，使第一阶段的信息能够在不放大误差的前提下，转化为第二阶段的真实生成收益。

---

## 三、本周阶段性结论

结合本周训练结果和代码审查，当前可以形成以下几个明确判断：

1. **推荐效果提升受阻的首要原因，已经基本定位到训练与推理流程，而不是单纯的模型结构。**

2. **Transformer 训练链路此前确实存在结构性问题，V4.6 已经完成第一轮修复，但训练稳定性仍需继续优化。**

3. **Set Predictor 当前更大的问题仍然在于“怎么用”，而不再主要是“第一阶段没有训成”。**

4. **从独立测试集结果看，`soft` 模式目前优于 `off`，且副作用明显小于 `hard`，更适合作为下一轮优化的主路线。**

5. **`hard` 模式虽然提升了集合匹配指标，但会损伤长度和顺序相关指标，当前不适合作为默认上线方案。**

6. **历史评估结果需要谨慎看待，后续应以修复后的独立测试集评估结果为准。**

---

## 四、当前存在的问题与风险

虽然当前链路已经能够稳定跑通，并完成了独立测试集评估，但仍存在几个关键问题：

- Set Predictor 单模型指标已经明显提升，但端到端收益仍然有限，说明当前主瓶颈已经转移到“第一阶段信息如何参与第二阶段解码”。
- `hard` 模式会把第一阶段误差直接放大到生成阶段，导致长度偏短、顺序质量下降。
- `soft` 模式虽然是当前更优路线，但提升幅度仍然不大，说明仅靠现有轻量偏置还不足以显著拉升最终推荐质量。
- Transformer 的独立基线仍然偏弱，尤其顺序相关指标整体不高，导致第一阶段即使给出更好的 token 集，也难以完全转化为高质量 workflow 序列。

换句话说，当前已经不是“系统没有跑通”或“Set Predictor 没训成”的问题，而是“二阶段联合方式还没有把第一阶段增益有效转化为最终序列质量”的问题。

---

## 五、下周工作计划

下周工作将围绕“继续优化联合推理方式”和“提升最终序列质量”两件事展开：

1. 以 `soft` 模式为主路线，继续做阈值和先验强度的小范围扫描，验证是否还能进一步提升集合和顺序指标。
2. 对 `hard` 模式补充 `--no-topk` 等实验，确认当前性能下降究竟来自硬约束本身，还是来自 Top-K 预算策略。
3. 继续梳理 Set Predictor 输出与 Transformer 解码之间的耦合方式，降低第一阶段错误被第二阶段放大的风险。
4. 在修复后的独立测试集评估体系上，稳定维护 `off / soft / hard` 三组可靠基线，作为后续版本迭代依据。

---

## 六、总结

本周最重要的进展，不只是完成了训练链路排查和 Set Predictor 重训，更在于**通过独立测试集上的真实对比实验，确认了当前系统的主要矛盾已经从“第一阶段能不能训起来”，转移到“第一阶段信息怎样更合理地参与第二阶段生成”**。这意味着后续优化重点将从单纯重训模型，转向联合推理机制本身的改造与收敛。
