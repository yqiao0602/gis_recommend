# 后续计划

## 0. 当前唯一主任务

当前阶段最重要的目标只有一个：

`先提升当前系统精度，并且把提升来源说清楚。`

这件事必须和另外两件事分开处理：

- 当前怎么提精度
- 系统最终要长成什么样
- 最后怎么做横向评估

如果三件事同时推进，会导致主线不断变化，最后无法判断性能提升到底来自哪个改动。

因此，当前阶段的原则是：

- 先固定 baseline
- 先做最小但最值的结构改动
- 再决定是否增加新的主模块
- 横向对比放到主线稳定之后

## 1. 当前阶段判断

### 1.1 Transformer V4.6 已完成的关键修复

- AR 主损失已可回传到 BERT，不再被 `detach()` 截断。
- `length_loss` 和 `task_loss` 已接通梯度，不再在 `no_grad` 中计算。
- 最优模型选择口径已从 `val_loss` 修正为 `AR-TokenAcc`。
- 评估测试集已切换为独立 `test_indices`，不再从全量样本抽取。

结论：

- V4.6 相比旧版本，训练逻辑已经明显更合理。
- 当前 transformer 主干可以继续保留，作为后续主线的核心生成器。

### 1.2 Set Predictor V3 当前状态

- 当前版本已经完成配置接通、兼容 checkpoint、采样平衡、best model 选择修正、多阈值输出等修复。
- 0406 重训结果表明：set predictor 本身训练是成功的，不是“训练失败”。

关键结果：

- Test `thr=0.7`: `F1=0.6438`, `P=0.5686`, `R=0.8046`, `AvgSize=11.1`
- Test `thr=0.8`: `F1=0.6571`, `P=0.6382`, `R=0.7280`, `AvgSize=8.8`

结论：

- set predictor 学到了有价值的集合级先验。
- 但它只能回答“哪些 token 可能出现”，无法单独解决顺序、长度和链级可用性。

### 1.3 0406 baseline 与 0407 阈值收尾实验结论

0406 baseline：

| 模式 | Set F1 | L2-Set F1 | LCS | Length Ratio |
|---|---:|---:|---:|---:|
| off | 48.53% | 57.20% | 0.3534 | 0.7415 |
| soft | 49.23% | 57.78% | 0.3579 | 0.7851 |
| hard | 49.69% | 58.46% | 0.3464 | 0.6540 |

0407 四组补充实验：

- `soft@0.75`: `Set F1=49.26%`, `L2-Set F1=57.81%`, `LCS=0.3577`, `Length Ratio=0.7776`
- `soft@0.80`: `Set F1=49.27%`, `L2-Set F1=57.80%`, `LCS=0.3578`, `Length Ratio=0.7708`
- `hard-threshold@0.75`: `Set F1=49.32%`, `L2-Set F1=58.10%`, `LCS=0.3401`, `Length Ratio=0.6301`
- `hard-threshold@0.80`: `Set F1=48.85%`, `L2-Set F1=57.65%`, `LCS=0.3350`, `Length Ratio=0.6076`

结论：

- `soft` 默认方案仍然是当前最稳妥、最均衡的 baseline。
- `soft` 模式对 threshold 变化并不敏感，继续围绕 `0.75 / 0.80` 扫描的收益已经很小。
- `hard-threshold` 即使去掉旧的 `top-k/count` 逻辑，仍然会明显伤害顺序和长度，因此这条路线可以停止继续投入。
- 当前主瓶颈已经不是“set predictor 没学到东西”，而是“set-level 信息没有被转化为 sequence-level 的最终决策”。

## 2. 当前主线的问题到底是什么

现有主线可以概括为：

`自然语言 -> transformer 生成 L3 序列 -> QGIS 映射 -> 最终结果`

当前最核心的问题不是单点模型不够强，而是整条链路缺了两个关键环节：

- 缺少全局候选选优：
  当前主评估链路本质上还是 beam 后直接取 `top-1`，没有真正的 candidate rerank / verify。

- 缺少显式规划：
  现在“做什么”和“怎么排”都压在 transformer 内部隐式学习，导致集合、顺序、长度纠缠在一起。

因此，后续方向不是继续围绕 threshold 或 set prior 微调，而是补齐链路结构。

## 3. 后续工作必须分阶段

### 阶段 A：当前提精度

目标：

- 固定当前最佳 baseline
- 先回答“当前问题是生成不到，还是选不好”

这一阶段只允许做最小必要改动，不同时新增多个核心模块。

### 阶段 B：中期架构升级

目标：

- 在 baseline 已稳定的前提下，引入更强的结构化规划能力
- 让系统从“单模型裸生成”过渡到“规划 + 生成 + 验证”的多模块协同

### 阶段 C：横向评估与论文对比

目标：

- 在系统主线稳定后，再做对外比较
- 包括与直接 LLM、渐进式 LLM、其他 baseline 的横向评估

这一阶段现在不作为主任务。

## 4. 明确执行顺序

### P0：已完成 baseline 锁定

当前 4 组补充实验已经完成，结论已确定：

- 当前最终 baseline 选择默认 `soft` 模式。
- `soft@0.75 / soft@0.80` 与默认 `soft` 基本打平，不再继续做更多 threshold 扫描。
- `hard-threshold` 路线即使显式使用 `--no-topk`，仍然明显伤害 `LCS` 和 `Length Ratio`，后续停止继续投入。

因此，P0 已完成，当前系统不再继续围绕 `threshold / set prior` 调参，而是正式转向链路结构改造。

### P1：先做 reranker / verifier，不先做 planner

这是下一阶段最优先、最小但最值的改动。

原因：

- 它离当前代码最近，改动成本最低。
- 仓库中已经有可复用模块。
- 它能先回答最关键的问题：
  `当前 top-N 候选里，到底有没有更好的答案，只是没被选出来？`

当前仓库可复用的部件包括：

- `interactive_system.py` 中的 GraphRAG + 结构化评分 + repair
- `chain_repair.py` 中的链修复逻辑
- `stage2_completion_pipeline.py` 中的“先骨架后补全”思路

P1 的目标不是重新设计主线，而是把主评估链路从：

`生成 -> 直接取 top-1`

改成：

`生成 top-N -> 全局打分 -> 选最优 -> 修复`

P1 必须附带做一个分析：

- `top-N oracle analysis`

要回答：

- `top-3 / top-5 / top-10` 中是否经常已经存在明显更好的候选

这个分析将直接决定 P2 的必要性：

- 如果 oracle gap 很大，说明先做 reranker 很值
- 如果 oracle gap 很小，说明问题更偏向“根本没生成到”，这时 planner 的价值会上升

### P2：增加骨架规划模块

P2 暂不与 P1 并行启动，而是在 P1 和 oracle analysis 之后再开始。

P2 的目标是：

- 把隐式规划显式化
- 降低 transformer 同时学习集合、顺序、长度的难度

建议的 planner 输出不是完整序列，而是更粗粒度的中间表示，例如：

- 必选 L3 token / 步骤族
- 可选步骤组
- 粗长度桶
- 粗阶段顺序模板

这一模块最值得参考的外部工作是 `MiniGeoSolver`，但需要准确理解它的两阶段逻辑：

- 阶段 1 不是“学单工具调用”
- 阶段 1 本质是：`任务 -> Framework`
- 阶段 2 本质是：`Framework + 任务 -> Workflow`

对应到我们系统，更合理的借鉴关系是：

- `MiniGeoSolver Framework`
  -> 我们的 `骨架规划模块输出`

- `MiniGeoSolver Workflow`
  -> 我们的 `条件化 L3 序列生成`

因此，MiniGeoSolver 的真正价值在于：

- 提供“先规划，再展开”的中间表示思路
- 支持我们后续把当前隐式规划显式化

而不是现在立刻替换现有主线为 Gemma/LoRA 方案。

### P3：联合训练与结构化输出

这一阶段放在后面，不提前展开。

可考虑的方向包括：

- planner 输出作为 transformer 条件输入
- set predictor 并入 planner head
- reranker 训练为候选排序模型
- 让 L3 生成从“裸 token 序列”向“带结构标签的序列”演进

## 5. Set Predictor 的最终定位

当前结论不是“删掉”或“继续单独强化”，而是：

- 现在保留
- 短期作为辅助规划信号
- 用于 soft prior 和 reranker 特征
- 中期并入骨架规划模块
- 不再视为最终精度提升的主抓手

原因：

- 它已经证明自己“有用”
- 但它的能力边界也已经很清楚，只靠它无法解决顺序和全局可用性问题

## 6. 横向评估现在怎么放

横向评估肯定要做，但不是当前主线。

原因：

- 当前系统还在变，过早横向对比会导致比较对象不断变化
- 现在最缺的不是“再找一个外部 baseline”，而是先把自己的主线稳定下来

建议的横向评估顺序如下。

### 6.1 先做内部消融

建议后续固定做这类对比：

- `V4.6`
- `V4.6 + set predictor`
- `V4.6 + set predictor + reranker/verifier`
- `V4.6 + set predictor + reranker/verifier + planner`

这样才能清楚说明每个模块带来的增益。

### 6.2 再做外部方法横向对比

等主线稳定后，再做以下外部比较：

- `LLM direct generation`
  直接从任务描述生成 workflow

- `LLM progressive generation`
  即 MiniGeoSolver 风格：先 `Framework`，再 `Workflow`

- 如条件允许，再加一个简单 retrieval baseline

这样论文或报告结构才会清楚：

- 先证明本系统内部每一步都有效
- 再证明最终系统相对外部 baseline 更强

## 7. 对 Geo-CLASS 和 MiniGeoSolver 的定位

当前两篇相关工作的重要性不同。

### MiniGeoSolver

当前参考价值最高。

原因：

- 它直接对应“自然语言 -> workflow”的生成问题
- 它最值得借的是“两阶段 / 渐进式 / 显式中间表示”
- 它主要服务于我们后续的 `P2 骨架规划模块`

### Geo-CLASS

当前不是主线参考，但后续仍然有价值。

它更适合服务于：

- 任务/功能/数据源的标准化知识体系
- 本体、知识图谱、GraphRAG
- 候选验证与知识检索底座

因此：

- `MiniGeoSolver` 更像“怎么生成”
- `Geo-CLASS` 更像“怎么构建知识底座与标准化语义空间”

## 8. 当前阶段的最终决策

当前阶段不要同时推进两个大模块。

明确顺序应为：

1. 以默认 `soft` 作为当前固定 baseline
2. 优先做 `reranker / verifier`
3. 做 `top-N oracle analysis`
4. 再决定是否启动 `骨架规划模块`
5. 主线稳定后，再做横向评估

也就是说，当前最关键的问题不是：

- “是不是要全面改成 MiniGeoSolver 风格”

而是：

- “当前 top-N 里有没有好候选，只是没选出来？”

把这个问题先答清楚，后续路线就会顺很多。
