  - 任务条件化的 L3 序列生成：见 src/gis_recommend/inference/infer_l3_candidates_v4.py

  所以它不是“照抄某个现成 workflow recommender”，而是把几条研究路线揉在了一起。更准确地说，你这个项目最接近的不是传统推荐系统，而是：

  - NL -> DSL / Program / Workflow 生成
  - 约束解码
  - 检索增强
  - 图谱辅助验证
  - generate-then-rerank / refine

  最适合你们参考的研究方向

  - NL2DSL / Workflow generation
      - Plan with Code 很像你们要做的“自然语言到 API / workflow 序列生成”，而且它明确研究了 RAG 对 NL2DSL 的帮助。
        链接：https://arxiv.org/abs/2408.08335
  - 约束解码
      - PICARD：把形式语言约束直接接进自回归解码。你们现在的 transition constraint、set prior，本质上就在这条路上。
        链接：https://arxiv.org/abs/2109.05093
      - NeuroLogic Aesque Decoding*：不是只做“合法性过滤”，而是让解码器在未来约束下做 lookahead。这个比你们现在的局部加偏置更高级。
        链接：https://arxiv.org/abs/2112.08726
  - 中间表示 / 先生成骨架再落地
      - Natural SQL：不是直接从 NL 生最终结构，而是先用更容易学的中间表示。对你们来说，对应“先预测 workflow skeleton / L2 plan，再生成 L3”。
        链接：https://aclanthology.org/2021.findings-emnlp.174/
  - 执行反馈 / 验证驱动修正
      - DART-SQL：问题重写 + execution-guided refinement。你们已经有 chain_validator，但还没真正把“验证反馈”回灌到 L3 序列修正里。
        链接：https://aclanthology.org/2024.findings-acl.120/
  - 工具/API 调用
      - Toolformer：核心不是聊天，而是“何时调用工具、调用哪个工具、怎么把结果并回推理”。这和你们的任务类型检索、图谱查询、QGIS 校验都很像。
        链接：https://arxiv.org/abs/2302.04761
  - 图谱增强
      - G-Retriever：图不是后处理附件，而是可检索、可对话、可定位证据的知识底座。你们现在 GraphRAG 的方向是对的，但还没前移到 L3 生成阶段。
        链接：https://arxiv.org/abs/2402.07630
  - 顺序推荐建模
      - SASRec、BERT4Rec 对你们不是直接可复用，但对“如何建模 operator sequence 的长程依赖”很有参考价值。
        链接：https://arxiv.org/abs/1808.09781
        链接：https://arxiv.org/abs/1904.06690

  我对你们现状的判断

  - 现在的主问题已经不只是“训练没训好”。
  - 你们最新结果表明：set predictor 本身训成了，但它接入解码器的方式还比较粗。
  - 也就是说，现在瓶颈更像是：
      - set-level 信息 和 sequence-level 解码 没有被很好融合
      - 生成后缺少一个强力的“判官模块”

  如果只允许加一个模块，我最推荐加：Reranker / Verifier
  不是再加一个生成器，而是加一个“候选序列重排序器”。

  原因很直接：

  - 你们现在 soft 比 off 好一点，hard 集合更像但顺序/长度变差。
  - 这说明 set predictor 提供的是有用信息，但“拿它去强控解码”会伤顺序。
  - 最自然的解法不是更强硬地约束，而是：
      - 先让 V4.6 生成 Top-K L3 候选
      - 再用一个 reranker 结合多种证据选最优

  这个模块如果落地，我建议它吃这些特征：

  - transformer 的序列 logprob
  - set predictor 的 set consistency 分数
  - transition 合法率
  - 长度偏差
  - task_type 匹配度
  - 检索到的相似历史 workflow 相似度
  - QGIS 候选链的 coverage / IO compatibility / validity

  这类模块往往比“继续硬调解码参数”更容易带来实质提升，因为它把“集合对不对”和“顺序对不对”分开建模了。

  如果允许加两个模块，优先级我会这样排

  1. 候选 reranker / verifier
  2. 历史 workflow 检索模块

  第二个模块的作用是：

  - 先从 11 万条已标注 workflow 里检索最相似的 task
  - 把这些 exemplar 作为生成条件或 rerank 特征
  - 这比纯靠一个生成模型记忆所有 task-pattern 更稳

  这条路也很契合 Plan with Code 和检索增强范式。

  如果目标是“大幅提升”，我不建议优先继续加 set predictor 分支
  我更建议转向这条新主线：

  - NL理解/路由
  - 候选生成
  - 检索增强
  - 验证/重排
  - 必要时局部修正

  也就是从“单模型尽量一次生成对”转成“生成 + 判别 + 修正”。

  一句话总结

  - 你们现在这套系统不是完全借鉴别人的成品，而是接近“NL2DSL + constrained decoding + graph-grounded verification”的混合架构。
  - 最值得参考的邻域研究，不是传统推荐，而是 NL2DSL / text-to-SQL / tool-use / graph-RAG / execution-guided refinement。
  - 如果只加一个最值模块，我建议加 L3 candidate reranker / verifier，这比继续往解码器里硬塞约束，更可能大幅提升最终推荐精度。

最终方案？

你现在这条主线可以概括成“NL -> transformer 生成 L3 序列 -> 映射 QGIS”，只是“规划”这一步现在是隐含在 transformer 里的。问题在于，隐式规划学得不稳时，模型会同时犯三类错：选错集合、排错顺序、长度失衡。你们 0406
  的结果已经说明了这一点：set predictor 能稍微改善集合，但一旦硬注入，顺序和长度就容易坏掉。这个现象本身就在说明，应该把“规划”和“最终选优”显式拆出来。

  我建议的整合版主线是：

  自然语言 -> 任务类型/任务分解 -> 骨架规划 -> 条件化 transformer 生成 top-N L3 候选 -> 映射出 top-M QGIS 候选 -> reranker / verifier -> repair -> 最终输出

  这里面两个新增模块职责不同，不重复：

  - 任务分解 / 骨架规划模块
    作用是前置收缩搜索空间，回答“这类任务大概需要哪些步骤、哪些必须出现、长度区间是多少、粗顺序是什么”。
    它解决的是“生成前”的问题。
  - candidate reranker / verifier
    作用是对已经生成出来的候选做全局判断，回答“哪条链整体最像可执行工作流”。
    它解决的是“生成后”的问题。

  所以它们其实一前一后，正好补齐你们当前最缺的两段。

  更具体一点，骨架规划模块不要一上来就做得太复杂。最小可用版我建议预测 4 类东西就够了：

  - must-have L3 tokens
  - optional L3 groups
  - 粗长度桶
  - 粗阶段顺序模板
    例如 数据准备 -> 空间分析 -> 后处理

  然后把这些结果喂给 src/gis_recommend/inference/infer_l3_candidates_v4.py：

  - must-have 作为正向约束
  - forbidden / unlikely 作为轻惩罚
  - 长度桶改 expected_length
  - 阶段模板做 transition bias，而不是硬 mask

  这样比现在只靠 set predictor 的 token 级偏置更像“显式规划”。

  而 reranker / verifier 模块，建议优先复用你们仓库里已经有的东西，不要另起炉灶。你们其实已经有成熟雏形了：

  - src/gis_recommend/pipelines/interactive_system.py:407 里已经有 GraphRAG + 结构化评分 + LLM 打分 + repair
  - src/gis_recommend/knowledge_graph/chain_repair.py:13 已经有修复器
  - src/gis_recommend/pipelines/stage2_completion_pipeline.py:34 已经有“骨架后补全”的思路

  现在真正缺的是：把这套逻辑从 demo / interactive 分支，正式接到 scripts/evaluate_system.py:205 的主评估链路里，而不是 beam 后直接拿 candidates[0]。

  如果按投入产出比排优先级，我建议：

  1. 先加 reranker / verifier
     这是最小改动、最快见效的。
     因为你们已经能生成多候选，只是主线没真正做全局选优。
  2. 再加 骨架规划模块
     它会进一步提升 top-N 候选质量，让 reranker 有“好候选可选”。
  3. 最后再考虑联合训练
     比如让 planner 输出作为 transformer 条件输入，或者把 set predictor 升级成 skeleton predictor，而不是停留在 present/absent 分类器。

  如果你问我这条整合路线在研究上像什么，它更接近这几个方向的组合，而不是某一篇单独论文：

  - 结构化约束生成：PICARD
    https://aclanthology.org/2021.emnlp-main.779/
  - 图检索与结构验证：GraphRAG
    https://www.microsoft.com/en-us/research/publication/from-local-to-global-a-graph-rag-approach-to-query-focused-summarization/
  - 检索增强的工具调用：Gorilla
    https://dblp.org/rec/journals/corr/abs-2305-15334
  - 大规模真实工具/API 选择：ToolLLM

  - 自然语言到结构化程序/DSL 的规划式路线：Plan with Code

  我的结论很直接：

  - 这两条路线确实应该合并
  - 先加 reranker / verifier，把你们已有多候选和验证模块接到主线上
  - 再加 任务分解 / 骨架规划，把“隐式规划”变成“显式规划”
  - 不建议继续只在 set prior 的软硬注入上打转了，收益已经接近天花板
