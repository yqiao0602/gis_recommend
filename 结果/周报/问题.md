  四个关键发现

  🔴 发现 1：SetF1 严重 misleading

  - Sample 3 SetF1=0.70 但方案是错的（一堆不相关夹一个 BandMath）

  🔴 发现 2：L3→QGIS 映射层有严重缺陷（比 L3 层更严重）

  Sample 2 是最惊人的：L3 完美到 SetF1=0.89，但到了 QGIS 链变成 []。说明映射层可能在某些情况下完全无输出。

  整体看，映射经常**"形似而神不似"**：
  - 模型学到了"这个任务周围常见算子"（所以算子集合重合度 SetF1 还能看）
  - 但没学到"解决这个任务需要的特定算子"（所以具体选择错）

  🔴 发现 3：栅格/矢量类型混淆

  Sample 5：矢量 tile 元数据任务 → 预测了 Clip raster + Mosaic
  Sample 6：LST 栅格任务 → 末尾出现 Multipart to singleparts（矢量算子）

  这种基础类型错误说明模型根本没建立"任务 → 数据模态"的映射。

  🔴 发现 4：核心操作缺失

  - Sample 4（EVI）：没 BandMath 就等于没算 EVI
  - Sample 7（日累计降水）：没累加操作就等于没做累计

---
  另一个隐藏问题：大小写

  训练数据里的算子是全小写（ee.image.select），但映射表里存的是驼峰（ee.Image.select）。step6 用 ImprovedOperatorMatcher.match_operator 去查——如果 matcher 做了 case-insensitive
  匹配，数据被正常标注（带错误映射）；如果没做，大量算子会 fall through 到 UNK。

  从样本看（ref_codes 里大量是有具体 L3 不是 UNK），matcher 应该做了不区分大小写的匹配。但这意味着 ee.Image.select（错映射到 Feature Stacking）和 ee.Imagecollection.select（对映射到 Select
  Bands）——同一语义的两条不同映射都被应用了，训练数据里这两种对同一事物的不同标签混在一起，模型当然学不稳。

  #2: ee.ImageCollection.map → Mosaic to New Raster

  这是系统性思维错误。GEE 的 .map() 是高阶函数（类似 Python 的 map()），它接受一个 function 遍历集合——它本身不是一个操作，它承载的是内部传入的 lambda。正确做法是跳过 map 本身，解析里面的函数。

  举例：coll.map(img => img.select(['B1']).multiply(10)) ——真实操作是 select + multiply，而不是 map。

  把 map 标成 Mosaic to New Raster 意味着：每个含 map 的脚本，训练数据里都会多一个"合成"假 token。Sample 4 的 map 出现 2 次，就多了 2 个假 Mosaic 标签。这是为什么模型特别喜欢输出 mosaic-like 算子。

  #3 & #11: filter / Filter.eq → Focal Statistics

  filter 和 Focal Statistics 连一个字都不搭。这个映射大概率是LLM 自动标注时对 "filter" 这个词的歧义没分清（GEE 的 "filter" 是集合筛选，GIS 里的 "filter" 才是滤波）。属于词面的混淆。
