# QGIS 扩产天花板对账 v1：修正架构调研的 5,000-7,000 估计

日期：2026-09-17
触发：owner 批准「对 5,400 个含 `processing.run` 的脚本跑提取器，产出规模/质量审计报告」。执行前核对发现：**提取审计已经存在三轮**（2026-07-21 分层、2026-07-22 多步 pilot、2026-09-14 全量漏斗），而 `cross_platform_architecture_survey_v1.md`（2026-09-16）给出的「天花板 5,000-7,000 行」采用的是**未过 admission 的原始口径**，与其自身提交时间之前两天的漏斗审计矛盾。本报告做对账并修正。

---

## 1. 结论（先行）

| 口径 | 数字 | 性质 |
|---|---:|---|
| 调研 v1 的估计 | 5,000-7,000 行 | ❌ 原始调用点外推，忽略已提交审计，**作废** |
| fail-closed 现池 | 629 行 | 当前 QGIS SFT 监督（train 616 / val 8 / test 5） |
| 已知零成本/低成本杠杆 | +100~200 | 描述事实化 +40~70（盘上已 verified）、词汇表授权 +30~100 |
| 审核待决 | +~50 | 18 条语义签名（review pack 字段空白）+ 31 条子工作流候选 |
| **fail-closed 天花板** | **~700-800 行** | 不买新能力的上限 |
| 新协议乐观上限 | ~1,000+ 行 | LLM 辅助恢复（route1 先例：3,554→315，8.9% verified） |

**对路线决策的直接影响**：方案 A（纯 QGIS 训练）被数据上限封死在 ~700 行量级。这是**测量结果，不是假设**。方案 B（双角色）与方案 C（修 L3）的 QGIS 侧锚定数据同样受此上限约束——两者的规模都必须来自 GEE 侧（8,283 行 + 257k 描述库）。

## 3. 调研 v1 错在哪里（三处）

1. **「10% 含 processing.run（≈5,400 个）→ 天花板 5,000-7,000 行」**：5,400 是真的，但 95%+ 过不了 admission——直线区域要求（4,030/4,264 deferred）、stable-94 全算子映射（103/234 unsupported）、依赖闭合、语义镜像去重（42→18）。**原始素材 ≠ 可监督样本**，这正是本项目 7-9 月反复证明的教训。
2. **「链长 median 2 / p90 16 / max 26」**：调用点计数口径，不是可采纳链长；p90 16 的长"链"大多正是被 deferred 的循环/分支结构。
3. **「可提取：QGIS 算子级源包链 1,351 行」**：无支撑报告，不可复核，从证据中移除。
4. **时间线错误**：全量漏斗审计 09-14 已提交，调研 09-16 却引用未经审计的口径——这是本次对账发现的最大疏漏。
