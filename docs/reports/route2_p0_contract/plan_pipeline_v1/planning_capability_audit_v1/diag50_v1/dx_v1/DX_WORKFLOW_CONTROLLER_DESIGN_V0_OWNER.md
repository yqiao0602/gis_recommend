我认为应该，而且这很可能是你后续把 DX-50 从“分阶段诊断系统”发展为“能够自我纠错的 GIS 工作流构建系统”的关键一步。

不过，我建议你不要把它简单理解成一个短期记忆系统，而是设计成一个有状态的工作流执行控制器（Workflow Controller）：它持续保存各阶段的产物、当前工作流状态、错误证据和重试历史，并根据错误发生的位置，决定是重选算子、重新检索，还是回退到规划阶段。

你现在的 DX 五阶段架构其实已经为此打好了基础。每个阶段独立调用、独立落盘，意味着将来可以只重跑某一阶段，而不必整条链重新生成。这是一个很有价值的设计优势。

## 一、先区分两件事：记忆与控制

你提出的机制实际上包含两个不同的功能。

- 短期工作记忆：记录当前任务已经做过什么、各阶段输出是什么、哪些决定被拒绝、为什么失败，以及当前工作流的状态。
- 反馈控制与回退：根据校验结果，判断应该修改哪一部分，并只重新运行必要的阶段。

前者回答“系统现在知道什么”，后者回答“系统接下来应该做什么”。

如果只保存历史而没有控制策略，系统只是能回放；如果只有回退策略而没有完整状态，系统又可能重复犯错、丢失之前的正确决策。因此，我建议二者配套设计。

## 二、建议的架构：在 S0–S4 外增加一个控制层

我不建议把重规划、重选逻辑直接塞进 S0 或 S3 的提示词里。更合理的是保留原来的五个阶段，在外部增加一个控制器。

### 任务输入

自然语言任务、数据与约束

Workflow Controller｜工作流控制器

读取当前状态 · 判断错误类型 · 选择回退位置 · 控制重试预算

### S0

规划

生成步骤、目的、输入输出与约束

### S1

检索

为每个计划步骤召回算子候选

### S2

选择

逐步选择算子、绑定参数或明确弃权

### S3

组合

生成带依赖关系的工作流

### S4

静态验证

检查结构、算子接地和可验证的执行约束

反馈判定

通过 → 输出；局部错误 → 局部重试；计划级错误 → 重规划；无法修复 → 明确失败

示意图中的反馈判定由控制器执行，不是额外要求一个大模型每次重新判断全部流程。

这里有一个重要原则：S0–S4 负责完成各自的工作，控制器负责判断整个任务下一步怎么走。

例如，S4 发现某一步缺少 `operator_id`，不需要让模型重新理解整项 GIS 任务；如果 S2 已经选错了算子，可以优先重选；只有发现原计划本身不合理时，才回到 S0。

## 三、短期记忆应该具体记录什么？

我建议将其设计为一个结构化的任务状态库，而不是把所有历史对话塞进模型上下文。

每个任务维护一份 `workflow_state`，至少包含以下内容：

| 状态字段                 | 作用                      |
| -------------------- | ----------------------- |
| `task_id` / `run_id` | 标识任务及本次执行版本             |
| `task_spec`          | 原始任务、数据条件、用户约束          |
| `plan_version`       | 当前规划版本，以及各步骤的稳定 ID      |
| `retrieval_results`  | 每步的检索查询、Top-10 候选、相似度分数 |
| `selection_results`  | 每步的选择结果、弃权原因、参数绑定       |
| `workflow_dag`       | 当前工作流节点、边、数据来源和依赖关系     |
| `validation_issues`  | 校验错误、对应步骤、错误类型与证据       |
| `retry_history`      | 已经在哪个阶段重试过、采用了什么策略、结果如何 |
| `budget`             | 剩余模型调用次数、总时间或 token 预算  |
| `status`             | 当前阶段、等待重试、已完成或无法修复      |

这里最重要的是 `plan_version`、`validation_issues` 和 `retry_history`。

比如，控制器发现第 4 步选错了算子，应该能知道：

- 第 4 步的原始规划是什么；
- 当时 S1 返回了哪些候选；
- S2 为什么选择了当前算子；
- S4 或其他校验器具体发现了什么问题；
- 之前是否已经尝试过相同的重选策略。

这样，下一次调用就不是让模型“再想想”，而是给它明确的错误证据和修改目标。

### 记忆要保存，但不能覆盖历史

你现有的 raw、gen、commit 三件套和哈希闭环仍然应该保留。新设计不应覆盖原始产物，而应在其上增加版本和状态索引。

例如：

```
runs/T-009/
├── S0/
│   └── plan_v1/
├── S1/
│   └── plan_v1/
├── S2/
│   └── plan_v1/
├── S3/
│   └── plan_v1/
├── S4/
│   └── validation_v1/
├── revisions/
│   ├── retry_001.json
│   └── retry_002.json
└── workflow_state.json
```

这只是一个示意目录。真正实施时，应复用现有的原子写入、提交标记和校验机制；每次重试创建新版本或新尝试记录，绝不直接修改已提交的原始产物。

另外，持久化记录和模型可见的短期记忆不是同一个东西。模型每次只需要读取与当前决策相关的状态摘要，不必把整条历史轨迹都塞入提示词，否则上下文会越来越长，反而容易干扰判断。

## 四、具体怎么回退？不能所有错误都回到 S0

我建议先建立一张明确的错误路由表。下面这张表可以作为第一版控制策略。

| 发现的问题                         | 优先动作                    | 是否需要重规划 |
| ----------------------------- | ----------------------- | ------- |
| S1 没召回正确算子，但算子库里存在            | 重检索：改进查询或扩大候选范围         | 通常不需要   |
| S1 有正确候选，S2 却弃权或选错            | 重选算子，提供候选差异和原始错误证据      | 通常不需要   |
| S1 候选不足，且发现原计划步骤本身表达不清        | 先澄清或修正步骤，再重新检索          | 可能需要    |
| S2 选择正确，但 S3 漏步骤、乱序或重复组合      | 重组工作流，保留正确的选择结果         | 通常不需要   |
| S4 发现 `operator_id` 缺失、参数字段缺失 | 局部修复结构化输出或重新生成相应步骤      | 不需要     |
| S4 发现输入输出类型不兼容                | 优先检查算子、参数及依赖关系；必要时重选或重组 | 视情况而定   |
| 发现 S0 漏掉任务的关键目标，或原计划存在根本性错误   | 回到 S0，重新规划              | 需要      |
| 多轮重试仍然失败，或者算子库不支持该任务          | 停止自动重试，返回明确失败或请求补充信息    | 不应无限重试  |

注意：这些错误路由只是初始规则，必须结合你实际的错误标签逐步验证，不能假设每个 S4 错误都能自动定位到唯一根因。

### 举个完整例子

假设任务要求识别研究区内 NDVI 高于某一阈值的区域。

第一次运行

S0：规划

生成 NDVI 计算、阈值处理和区域输出等必要步骤。

S1：检索

阈值处理步骤的 Top-10 中包含 Raster Calculator。

S2：选择

模型却选择了一个只负责筛选矢量要素的算子。

S3/S4：组合与验证

工作流可能在结构上成功生成，但数据类型校验发现栅格输入与矢量选择操作不兼容。

### 控制器的决策

读取 S4 错误 → 定位到阈值处理步骤 → 读取该步骤的原始规划和 S1 候选 → 重新运行 S2。

如果重选成功，保留其他正确步骤，仅重新组合 S3 并复查 S4。无需重新运行 S0。

如果重选后仍然不兼容，控制器可以进一步检查是否是检索遗漏、参数理解错误或规划步骤表达不清，再决定是否回退到 S1 或 S0。

这才是分阶段架构真正的优势：错误可以沿着依赖关系向上定位，而不是每次都让整个系统从头生成。

## 五、但这里有一个更关键的问题：如何判断什么时候该重规划？

这部分不能完全交给大模型自由判断，否则很容易出现反复循环：

重选算子 → 仍然失败 → 再选一次 → 仍然失败 → 重新规划 → 又回到原来的选择。

我建议采用三种机制。

### 1. 基于错误证据的触发规则

确定性错误优先由程序判断，例如：

- `operator_id` 不存在；
- 必需参数缺失；
- 输入输出类型不兼容；
- 依赖节点不存在；
- 工作流中出现循环依赖；
- 某个必须步骤没有对应操作。

这类错误不需要额外调用大模型来判断“有没有错”。控制器可以直接生成结构化的错误报告。

### 2. 基于语义证据的触发规则

有些错误无法通过静态校验器发现，例如：

- 计划中包含一个与任务目标无关的步骤；
- 所选算子名称看起来相似，但功能不符合目标；
- 工作流虽然能执行，却没有真正实现任务要求。

这时可以让独立评估器或模型进行针对性审查，但要明确它只是一个可能存在误判的评估组件，而不是绝对正确的裁判。

### 3. 限制重试次数，并记录失败原因

建议第一版先采用简单、可解释的策略：

- 局部选择错误：优先进行有限次数的 S2 重选；
- 检索候选不足：尝试有限次数的 S1 重检索；
- 工作流组合错误：有限次数重跑 S3；
- 明确的规划错误：才允许回到 S0；
- 达到预算上限后停止，记录无法解决的问题。

具体重试次数应通过实验确定，不必现在就固定一个看似精确的数字。

每次重试都必须改变某个明确的条件，例如候选集、错误提示、参数约束或规划版本。如果输入、候选和提示都不变，只是重复调用同一个模型，通常没有充分理由期待结果会稳定改善。

## 六、从研究角度看，这套机制还有一个价值

你未来不只是在做一个能够反复调用模型的工程系统，还可以研究一个更有意义的问题：

当 GIS 工作流生成出现错误时，系统能否根据错误类型选择正确的修复层级，并以较低的额外调用成本提高最终可用率？

这可以设计成一个独立的实验。

| 对照方案     | 运行方式                  | 研究目的           |
| -------- | --------------------- | -------------- |
| Baseline | S0–S4 一次执行，不做反馈修复     | 确定初始可用率        |
| 全链重试     | 失败后重新生成整个工作流          | 测量简单重试的效果与成本   |
| 局部重试     | 仅重跑出错阶段及受影响的下游阶段      | 测量局部修复是否更高效    |
| 诊断式回退    | 根据错误类型选择重选、重检索、重组或重规划 | 验证错误定位和回退策略的价值 |

核心评价可以包括：

- 最终可用工作流比例；
- 关键错误修复率；
- 原本正确的步骤被破坏的比例；
- 每个成功工作流的平均模型调用次数；
- 额外 token 消耗与执行时间；
- 多轮修复后仍然失败的比例。

其中，“原本正确的步骤被破坏的比例”特别值得关注。因为如果重规划能够修复一个遗漏，却同时改变了五个原本正确的步骤，那么它可能不是最优修复策略。

实验时还应控制调用预算，并保留未修复基线；否则，全链重试与局部重试之间的成本比较可能不公平。

## 七、我的最终建议

你现在不需要立即引入一个复杂的长期记忆系统，也不需要额外训练一个专门的重规划模型。

我建议按以下顺序实现：

1. 先保留现有 DX-50 的五阶段设计和完整落盘机制。 它是后续可复现研究的基础。
2. 在现有产物之上增加 `workflow_state` 和版本管理。 让系统能够知道每一步做过什么、当前处于什么状态。
3. 先实现基于确定性错误的局部回退。 优先处理缺失字段、参数错误、类型不兼容和依赖断裂。
4. 再增加基于语义错误的 S2 重选与 S0 重规划。 先用 DX-50 中已审查的失败样本验证策略，再逐步扩大范围。
5. 最后比较局部修复、全链重试和诊断式回退。 通过可用率、修复率和调用成本判断这套机制是否真正有价值。

一句话概括：你需要的不是一个让模型记住所有历史的聊天记忆，而是一个以不可覆盖的阶段产物为证据、以结构化任务状态为依据、能够进行局部回退和受控重规划的工作流控制器。

这既能利用你当前 DX 五阶段解耦的架构优势，也能让后续的错误修复机制具备可追踪、可复现和可量化评估的研究基础。
