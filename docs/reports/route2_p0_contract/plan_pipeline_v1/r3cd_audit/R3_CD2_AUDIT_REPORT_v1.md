## F1. run-cap 的真面目：RLE（游程压缩），删除的是"循环迭代次数"，不是操作类型

对全部 101,513 行做结构验证：

- `semantic_chain_rle` 是 raw 的**保序子序列**（101,475/101,513 = 99.96%；mismatch = 0）。
- 被删的 976,094 步**全部是连续重复操作的折叠**（原始 GEE 脚本里的逐波段/逐要素/逐年份循环）。
- **family 多样性零损失**：raw 30 种 = final 30 种；被删最多的 family（AGGREGATION 213k、
  ATTRIBUTE_FILTER 201k、RASTER_LOAD 167k…）同时也是 kept 里的主要 family——
  **被删步骤不比保留步骤更"任务特异"，它们是同族操作的重复迭代**。
- 游程长度分布长尾：最长单游程 **600 次重复**（一个循环跑 600 次同类操作）。

**含义**：run-cap 没有删掉任何操作种类，它把 Plan 长度从"workflow 规模（含迭代）"
重新定义为"**不同阶段的个数**"。假说 A（"run-cap 破坏了任务特异信息"）**不成立**。

## F3. owner 两个假说的裁定

**假说 B 成立（数据本身缺乏足够的 Task→Workflow 对齐监督），附带一个重要细化**：

- Task 文本对 workflow 长度的信号在源头就弱（ρ≈0.19-0.25），RLE 后无显著恶化（ρ≈0.15-0.21）。
- **细化**：run-cap/RLE 是一个**表示选择**——它把"循环迭代"从 Plan 中抽象掉了
  （32.1% 的 instruction 含 each/every/per/all 迭代措辞，但 Plan 表示无法表达迭代次数）。
  因此即使 Task 完美描述了原始脚本，Plan 长度也≠任务描述的规模。
  这不是管道事故，而是**"Plan = 阶段序列"这个 Contract 与"任务描述 workflow 规模"之间的表示鸿沟**。

## F4. 对下一步的含义（供 owner 裁定）

1. **修 run-cap 不是修复方向**——它没有删任务特异信息；把迭代展开回去只会让 Plan 更长、
   监督更重复，且与 W3 的 family-sequence 评测口径不匹配。
2. **真正的缺口在 Task 表示**：当前 instruction 不指明"该任务需要哪些阶段、多少数据组、
   什么规模的迭代"。要让 W3 的 Task→Plan 成为可学习的条件映射，任务侧需要
   **结构化/半结构化的 workflow 规格**（子目标、数据组、输出要求）——
   这是数据工程/Contract 重设计（owner 级决定），且意味着重建任务文本或改用
   script 派生的结构化任务表示。
3. **TRUNC-exclusion / 上游 run-cap 修复**：均降级——在表示鸿沟未解决前，
   它们对 W3 的预期影响有限（次级因素）。
4. ** Stage-1 诊断链闭合**：
   `W3≈0.50 ← 长度/结构条件信号弱（源头 ρ≈0.2，RLE 继承）← 任务=散文摘要 + Plan=阶段序列`
