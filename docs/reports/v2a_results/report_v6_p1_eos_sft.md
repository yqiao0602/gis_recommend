## 2. 失败机制分析

1. **终止确实被修复了一半**：truncated 主因行 dev 42→24、test 46→35；重复跑马 0.39→0.22。λ=20 的 EOS 强化在"学会停"上是有效的。
2. **但代价是生成质量整体退化**：E1 出现了 C0 几乎没有的新失败类别（dev: no_json 12 / shape 3 / json_error 5；test: no_json 10）；invalid operator 0.39→0.53——提前停/急着停使 JSON 不完整或算子名更破碎。conditional F1（纯质量口径）的下降说明**这不是可靠性换算质量的问题，是质量本身受损**。
3. **方向解释**：λ=20 使行尾 EOS 的梯度占整个 target loss 的 ~20/150 ≈ 13%，模型学到的不只是"完整后停"，还有"早停的风险可以接受"——两类信号在单 token 加权下不可分离。

## 3. 三层证据链汇总（P0+P1 两轮干预后的 reliability 瓶颈现状）

| 干预 | 层 | hit_cap | 质量代价 | 净效应 |
|---|---|---|---|---|
| ngram8 解码约束 | 解码 | 35%→15% | parse_ok↓ 名称损坏↑ | **负**（report_v4） |
| EOS λ=20 SFT | 训练目标 | 35%→20% | conditional F1 −0.06、invalid↑ | **负**（本报告） |
| canonicalization（P0） | 后处理 | 不变 | 无 | **+0.03~0.04 E2E**（report_v5） |

**结论**：终止失控不是"缺一个停止信号"的单点问题——加大 EOS 监督与解码层禁重复都以质量为代价。剩余路径：catalog 语法约束解码（P2，路线图最后一项）或回到数据侧（如 gold 重复算子的去重审计——36% 行含合法重复本身可能放大了模型对重复的困惑）。
