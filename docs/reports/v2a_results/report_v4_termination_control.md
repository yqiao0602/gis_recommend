| parse_ok | 0.633 | 0.592 | −0.041 ❌ |

**跑马确实被压掉一半多，但换来的不是可解析输出，而是新的失败模式**：json_error 从基线的"几乎全是跑马"（44 失败中 42 跑满 512）变成 48 个 json_error 中仅 18 个跑满——**30 行提前终止但 JSON 仍是坏的**，且算子名损坏加重（raw P 0.360→0.260）。

## 2. 机制：gold 的合法重复被解码约束误伤

冒烟阶段的逐行预测对比已给出证据，全量数字证实：

1. **gold 链本身含重复算子**（report_v1 已记录："gold 链含 extraction 产生的重复算子"）。同一算子连写两次，其 8-gram（完整算子名+JSON 语法）即重复 → 被 `no_repeat_ngram_size=8` 禁止 → 模型被迫输出变形名称或提前断掉 JSON。
2. **`repetition_penalty` 更糟**（1.1/1.15 都测了）：它惩罚的 `native:`/`gdal:` 共享前缀 token 正是所有算子名的组成部分 → 冒烟上 operator F1 直接归零。
3. **`no_repeat_ngram_size=3` 是灾难**：JSON 多 process 块的天然结构 3-gram（`"process_id": "p…`）被禁 → parse_ok 0.75→0.25。

**根本原因**：重复失控与合法重复在 token 层不可区分。散文工具（ngram/penalty）无法分辨"病态循环"与"gold 要求的同一算子第二次出现"。

## 4. 对改进优先级列表的修正（report_v3 §3）

原优先级 1"序列终止控制（+0.15 量级）"**在解码层不可得**。剩余可行路径：

1. **② 算子名规范化（后处理，零成本，立即可得）**：canon 诊断已量化 +0.087（条件口径 0.301→0.388；P 0.360→0.538）。作为后处理层正式化即可，无需任何训练/解码改动。
2. **① 终止控制的训练层路线**：eos_lambda 加权 SFT（M3-P1 已有同类解法可复用）——训练目标层强化 EOS，不误伤合法重复。需要重训（A' 变体）。
3. **catalog 约束解码（语法层）**：真正的根治路线——JSON grammar + 算子 trie 约束，在结构层允许算子重复、只在 process 计数层面控制失控。工程量最大。
