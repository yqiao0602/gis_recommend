# 自然语言到 GIS/QGIS 工作流系统流程总结

日期：2026-05-31

## 1. 当前系统目标

当前系统的目标不是直接让大语言模型生成 GIS 工作流，而是构建一条相对可控、可评测、可逐步增强的工作流推荐链路：

```text
用户自然语言任务
  -> 任务结构化
  -> 小模型生成 L3 工作流
  -> QGIS 算子链落地
  -> GraphRAG / Neo4j 提供算子知识增强
  -> LLM 辅助解释、补全、审查和最终交互输出
```

其中，小模型负责核心规划，QGIS 落地模块负责把抽象步骤接到具体平台算子，GraphRAG 提供结构化证据，LLM 负责自然语言理解、交互解释和受约束的辅助修正。

## 2. 原始设想流程

原本设想的系统流程可以概括为：

```text
用户输入自然语言任务描述
  -> 模型理解任务
  -> 输出对应算法步骤（L3 token / L3 code）
  -> 根据 L3 步骤找到对应 QGIS 算子
  -> QGIS 算子和关系存入 Neo4j，形成 GraphRAG
  -> LLM 结合 GraphRAG 判断 QGIS 算子链是否合理
  -> 输出最终推荐结果和解释
```

这个流程的优点是完整：从自然语言输入，到抽象规划，再到 QGIS 平台算子，最后还能给用户解释。

但其中最需要谨慎的是 LLM 的位置。如果直接让 LLM 判断“这个 QGIS 链是否合理”，就会出现一个问题：默认 LLM 是 GIS/QGIS 专家，但我们又缺少证据证明 LLM 的判断一定正确。这会导致系统正确性变成“LLM 说对就是对”，证据链较弱。

因此，LLM 不能作为无约束的最终裁判，而应作为受规则、图谱证据和候选空间约束的辅助模块。

## 3. 推荐的完整系统架构

更稳妥的系统架构如下：

```text
用户自然语言输入
  -> LLM 将自然语言任务结构化
  -> 小模型根据结构化任务生成 L3 工作流
  -> 规则检查 L3 工作流是否明显可用
  -> QGIS landing 根据 L3 和任务信息召回 QGIS 候选算子链
  -> Neo4j / GraphRAG 提供算子定义、输入输出、模态、常见组合和相似案例
  -> LLM 在证据约束下做解释、补全建议或候选排序
  -> 系统输出推荐 QGIS 算子链、备选方案和自然语言说明
```

可以进一步拆成四个角色：

| 模块 | 主要职责 | 是否作为最终裁判 |
| --- | --- | --- |
| LLM 输入层 | 把用户自然语言任务转成结构化任务描述 | 否 |
| 小模型 | 生成 L3 工作流，是核心规划器 | 是核心生成模块，但结果需检查 |
| QGIS landing + GraphRAG | 检索 QGIS 候选链，提供算子和图谱证据 | 提供证据和候选空间 |
| LLM 输出/辅助层 | 解释结果、辅助补全、候选排序、回答用户问题 | 否，需受证据约束 |

## 4. LLM 在入口处的作用

用户输入往往是自由自然语言，小模型未必适合直接理解所有口语化、模糊化任务。因此入口处使用 LLM 是合理的。

例如用户输入：

```text
我想把道路周围 500 米范围内的建筑筛出来，再按行政区统计面积。
```

LLM 可以先转换为结构化任务：

```text
任务类型：矢量空间分析
数据对象：道路、建筑、行政区
核心操作：缓冲区、空间叠加、统计汇总
数据模态：vector
输出目标：统计道路影响范围内建筑在各行政区中的面积
```

这样小模型接收到的是更稳定的结构化任务表示，而不是完全自由的自然语言。

这一层的 LLM 不直接生成最终工作流，而是做任务规范化，因此风险相对可控。

## 5. 小模型的核心位置

小模型仍然是系统的核心规划器。它的职责是根据结构化任务生成 L3 层面的 GIS 工作流。

这一点很重要。如果直接让 LLM 生成完整 GIS/QGIS 工作流，那么前面训练的小模型、DPO 偏好训练、L3 体系和评测结果都会被弱化。

因此系统应明确：

```text
LLM 不替代小模型做核心规划；
小模型负责 L3 工作流生成；
LLM 只做任务结构化、证据约束下的补全/解释/候选排序。
```

当前实验结论也支持这个分工：

- 在 GEE/遥感任务上，小模型的 L3 规划能力已经基本成立；
- 在传统矢量 / QGIS-native 任务上，小模型仍然容易偏向遥感栅格模板；
- 因此下一步需要补充高质量 QGIS/矢量任务数据，用于增强小模型的矢量规划能力。

## 6. QGIS landing 和 GraphRAG 的作用

小模型输出 L3 工作流后，系统需要把抽象步骤落到 QGIS 具体算子。

QGIS landing 的作用是：

```text
L3 工作流 + 任务信息
  -> 召回 QGIS 候选算子链
  -> 根据模态、步骤覆盖、链长、算子组合合理性排序
  -> 输出 QGIS 算子链候选
```

GraphRAG / Neo4j 的作用是增强这一过程。它不只是存储算子列表，而是提供结构化证据：

- QGIS 算子功能说明；
- 输入输出类型；
- 矢量/栅格模态；
- 常见前后继关系；
- 相似历史工作流；
- QGIS 算子与 L3 或 QGIS 原生标签之间的桥接关系。

GraphRAG 的价值在于减少 LLM 幻觉。LLM 不再只根据语言常识判断，而是基于检索到的算子知识和工作流证据进行解释或建议。

## 7. 中间矫正环节的矛盾

当前最矛盾的地方是：

```text
小模型有时输出不准，需要 LLM 帮助矫正；
但如果让 LLM 直接自由矫正，又会变成 LLM 参与核心规划甚至覆盖小模型。
```

这个矛盾不能靠“完全不用 LLM”解决，也不能靠“完全相信 LLM”解决。

更合适的定位是：

```text
LLM 是证据约束下的修正建议器，而不是自由规划器。
```

也就是说，LLM 可以参与补全和纠错，但必须受到约束：

1. 不能凭空改；
2. 只能基于用户任务、小模型输出、QGIS 候选链、规则检查和 GraphRAG 证据提出建议；
3. 优先在系统召回的候选空间中选择或重排；
4. 每次修改都需要说明依据；
5. 修改后仍需通过规则检查或人工审查样本校准。

## 8. LLM 可以修正哪些问题

LLM 辅助修正可以分为不同等级。

### 8.1 局部缺失步骤

例如用户任务是：

```text
道路缓冲并裁剪研究区
```

小模型只输出了缓冲区，漏掉裁剪。

这种情况可以让 LLM 根据任务文本和候选链提示“缺少裁剪步骤”，并从 QGIS 候选中选择包含裁剪的链。

### 8.2 模态冲突

例如用户任务是矢量分析，但小模型输出了栅格计算、栅格裁剪等步骤。

LLM 可以基于任务结构化结果和 GraphRAG 证据指出：

```text
当前链偏栅格，不适合该矢量任务。
```

然后在 QGIS 候选链中选择更符合矢量分析的方案。

### 8.3 顺序不合理

例如先统计再裁剪，或者先导出再处理。

这类问题可以通过规则检查发现，再由 LLM 生成解释或给出候选重排建议。

### 8.4 完全任务理解错误

例如用户要 Voronoi 服务区，小模型却输出植被指数计算。

这种情况不应让 LLM 自由生成一条全新链并直接采纳。更合理的是触发 fallback：

```text
小模型规划明显失败
  -> 使用 GraphRAG / QGIS 候选检索
  -> LLM 在候选空间中辅助选择
  -> 输出时标记为“检索/LLM 辅助方案”
```

这样可以保留系统透明性，不把 LLM 伪装成小模型能力。

## 9. 三层决策机制

建议把系统决策分为三层：

```text
Level 1：小模型直接规划
  适用于 GEE/遥感任务，当前能力较强。

Level 2：LLM 证据约束补全
  适用于缺少个别关键步骤、顺序略有问题、轻微模态冲突。

Level 3：GraphRAG 检索 fallback
  适用于小模型明显不适配的 QGIS-native / 传统矢量任务。
```

这套机制的优点是：

- 保留小模型作为核心规划器；
- 承认小模型在部分任务上的不足；
- 允许 LLM 帮助修正，但不让 LLM 无约束替代小模型；
- 对明显 fallback 的样本保留标记，便于后续评测和分析。

## 10. LLM 在输出端的作用

输出端使用 LLM 是合理的，尤其适合以下任务：

- 把 QGIS 算子链翻译成用户能理解的步骤；
- 解释某个 QGIS 算子的作用；
- 解释参数含义，例如 buffer distance、dissolve、CRS、clip layer；
- 根据 RAG 检索到的算子说明回答用户追问；
- 给出结果风险提示，例如“该方案需要输入图层坐标系一致”。

例如系统内部输出：

```text
native:buffer -> native:clip -> native:dissolve
```

LLM 可以输出给用户：

```text
推荐流程：
1. 先对道路图层建立缓冲区；
2. 再用研究区边界裁剪缓冲区结果；
3. 最后按需要融合结果，得到最终影响范围。
```

这类输出不改变核心规划结果，只是解释和交互，因此风险较低。

## 11. 最终输出一条还是多条

建议系统内部保留多条候选，用户默认展示一条主推荐。

原因是 GIS 工作流天然存在多解。同一个任务可能有多种合理实现方式。例如“筛选道路影响范围内建筑”可以使用：

- buffer + intersection；
- buffer + select by location；
- buffer + spatial join；
- clip + statistics。

因此，推荐机制可以设计为：

```text
内部保留 Top-k 候选链，例如 3-5 条；
默认向用户展示 Top-1 推荐链；
同时提供 1-2 条备选方案及适用场景。
```

面向用户的输出可以是：

```text
推荐方案：
道路缓冲 -> 选择缓冲区内建筑 -> 按行政区统计面积

推荐理由：
该方案覆盖了缓冲区分析、空间筛选和统计汇总三个关键步骤，适合当前任务。

备选方案：
如果需要保留完整叠加结果，可使用“缓冲区 -> 相交分析 -> 字段统计”。
```

这样既保证主结果简洁，也保留 GIS 多解任务的灵活性。

## 12. 下一步 QGIS 数据的作用

当前模型的主要短板是传统矢量 / QGIS-native 任务。原因是现有训练数据主要来自 GEE/遥感栅格场景，模型容易把矢量任务也套到遥感栅格模板上。

因此下一步需要构建高质量 QGIS/矢量任务样本。但重点不是直接把原始 QGIS 脚本加入训练，而是先构造高质量监督样本：

```text
自然语言任务描述
  -> 结构化任务表示
  -> 合理 L3 矢量工作流
  -> 对应 QGIS 算子链
  -> 好链 / 坏链 preference 对
```

这些样本可以用于 preference 训练，使小模型学会：

- 遇到矢量任务时不要套遥感栅格模板；
- 识别 buffer、clip、dissolve、join、reproject、fix geometry 等矢量关键步骤；
- 对 QGIS-native 任务保留必要的原生操作；
- 在多条候选链中选择更符合任务目标的链。

## 13. 推荐的系统表述

可以将最终系统表述为：

> 本系统采用“小模型规划 + 知识图谱增强 + LLM 辅助交互与修正”的协同框架。LLM 首先将用户自然语言任务转为结构化输入，小模型负责生成 L3 层面的 GIS 工作流；随后系统结合 QGIS 算子库和 Neo4j/GraphRAG 检索候选 QGIS 算子链。LLM 不作为无约束的最终裁判，而是在规则检查、图谱证据和候选空间约束下，对小模型输出进行解释、局部补全、候选排序和用户交互。对于小模型明显不适配的任务，系统触发 GraphRAG 检索式 fallback，并保留该标记用于评测和后续训练。

更简洁的版本是：

> LLM 负责入口任务结构化和出口解释交互，小模型负责核心 L3 规划，GraphRAG/QGIS landing 负责算子链检索与约束；中间的合理性判断由规则、图谱证据、候选评分和人工校准共同完成，LLM 只做证据约束下的辅助修正，而不是最终裁判。

## 14. 当前阶段结论

当前系统已经可以证明：

- 自然语言到 L3 工作流的遥感/GEE 分布规划能力基本成立；
- L3 到 QGIS 算子链的规则落地链路已经打通；
- QGIS 落地仍有模板化问题，不能声称已经达到严格语义正确或参数级可执行；
- 传统矢量和 QGIS-native 任务是下一阶段主要瓶颈；
- LLM 可以合理用于入口结构化、出口解释、GraphRAG 约束下的补全和候选排序；
- LLM 不应作为无校验的最终正确性裁判。

因此，后续工作应重点转向：

1. 构建高质量 QGIS/矢量任务样本；
2. 生成或人工审查 preference 训练对；
3. 增强小模型的矢量规划能力；
4. 建立 GraphRAG 证据约束下的 LLM 辅助修正机制；
5. 用人工 gold set 校准 LLM 判断和 QGIS landing 结果。
